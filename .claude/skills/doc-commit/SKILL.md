# Doc Commit — 작업 결과를 문서에 앉히고 커밋한다

## 이 스킬이 푸는 문제

이 프로젝트는 **문서가 다음 세션의 유일한 기억**이다. 대화는 사라지고 코드만 남는데,
코드는 *"무엇을 했는가"* 는 말해도 *"왜 그렇게 정했고 무엇을 하지 말아야 하는가"* 는 말하지 못한다.

실제로 이 프로젝트에서 반복된 사고가 그것이다(CLAUDE.md 변경 이력):

- **`FOLLOWUPS #10` 의 원인 2건이 이미 해소됐는데 항목이 안 고쳐져, 리더가 낡은 자료를 설계 판정에 넘겼다.**
- **같은 항목을 세 번 뒤집어** 개발자에게 모순된 지시가 갔다 — 판정이 메시지 이력에만 있었기 때문이다.
- **빌드 교체 사고 3회·축척 왕복 3회의 교훈이 워크스페이스 문서에만 있어** 다음 작업으로 넘어가지 않았다.

셋 다 *"어딘가에는 적혀 있었다"*. 문제는 **적힌 자리가 틀렸다**는 것이다.
그래서 이 스킬의 절반은 «무엇을 쓸까» 가 아니라 **«어디에 쓸까»** 다.

## 1. 입력 모으기 — 기억에 의존하지 않는다

순서대로 실제로 읽는다. **읽지 않고 요약하지 마라.**

| 순서 | 원천 | 명령 |
|------|------|------|
| 1 | **메모리** | `ls ~/.claude/projects/-Users-koscom-IdeaProjects-koscomlabor/memory/` → `MEMORY.md` 와 각 파일 |
| 2 | **마지막 문서 커밋 이후 변경** | `git log --oneline -30` · `git log -20 --format='%h %s%n%b'` |
| 3 | **작업 트리 상태** | `git status --short` (커밋 안 된 것이 남아 있으면 먼저 처리) |
| 4 | **현행 문서** | `CLAUDE.md` 변경 이력 표 마지막 행 · `_workspace/FOLLOWUPS.md` 전체 |

⚠ **커밋 메시지가 1차 사료다.** 이 프로젝트의 커밋 본문에는 «무엇을 실측했고 무엇을 버렸는가» 가
들어 있다. 문서에 옮길 문장의 근거는 대부분 거기 있다.

⚠ **`_workspace/` 는 지우지 않는다.** 검증 이력·감사 추적용이다(오케스트레이터 Phase 6).

## 2. 배치 판정 — 이 사실은 어느 문서의 것인가

**하나의 사실은 한 곳에만 적는다.** 두 곳에 적으면 언젠가 한쪽만 고쳐진다(요구 88 · 한 출처).

| 사실의 성격 | 갈 곳 | 판정 질문 |
|---|---|---|
| **다음에 같은 실수를 막는 규칙** | `.claude/skills/*/SKILL.md` | *"다른 작업에서도 적용되는가?"* → 예 |
| **이 코드에서만 통하는 함정** | **소스 주석** (문서 아님) | *"이 파일을 여는 사람만 알면 되는가?"* → 예 |
| **하네스 구성 자체가 바뀜**(스킬·에이전트 추가/개정) | `CLAUDE.md` 변경 이력 표 | *"스킬이나 에이전트 파일을 고쳤는가?"* → 예 |
| **미해결로 남긴 것** | `_workspace/FOLLOWUPS.md` | *"범위 밖으로 밀었는가?"* → 예 |
| **이번 실행의 산출물·판정** | `_workspace/0X_*.md` | *"이번 라운드의 기록인가?"* → 예 |
| **세션 간 사실**(사용자·환경·도구) | **메모리** | *"코드·문서에 적을 자리가 없는가?"* → 예 |
| **프로젝트를 처음 여는 사람이 알아야 할 것** | `README.md` | *"실행법·구조가 바뀌었는가?"* → 예 |

### ⚠ 소스 주석에 이미 있는 것을 문서로 복사하지 마라

이 프로젝트의 소스 주석은 **이례적으로 두껍고, 그것이 설계다.** `RallyMap.tsx` 하나에
실측값·버린 안·되돌리지 말아야 할 이유가 들어 있다. 그것을 SKILL.md 로 옮기면
**두 벌이 되고, 코드를 고치는 사람은 주석만 고친다.**

**문서로 올릴 것은 «일반화된 규칙» 뿐이다.**

> 예 — 2026-08 로드뷰 작업
> - 소스에 남길 것: *"`getProjection().fromOffsetToCoord` 는 세로를 무시한다(거리 226m 고정)"*
>   → **`RallyMap.tsx` 주석.** 이 API 를 쓰는 곳은 여기뿐이다.
> - 스킬로 올릴 것: *"문서에 없는 API 에 기대는 기능은 **기능 감지 + 조용한 비활성**으로 감싸고,
>   실패해도 기존 경로가 남게 한다"*
>   → **`union-webapp-dev`.** 다음에 다른 API 에서도 똑같이 적용된다.

## 3. 파일별 규칙

### 3.1 `CLAUDE.md` — 변경 이력 표

**하네스가 바뀐 경우에만 행을 추가한다.** 콘텐츠·기능 작업은 여기 오지 않는다.

```
| 날짜 | 변경 내용 | 대상 | 사유 |
```

- **날짜**: 오늘(`YYYY-MM-DD`). 상대 표현 금지.
- **변경 내용**: 무엇이 어떻게 바뀌었는지. 절 번호가 있으면 함께(`§5.3 문안 절제 절 신설`).
- **대상**: 실제 파일 경로. `skills/union-fact-check §5.3` 처럼 절까지 적는다.
- **사유**: ★ **«무엇이 있었기에 이 규칙이 생겼는가»** 를 적는다. 이 표의 사유 칸이
  긴 것은 실수가 아니다 — **재발을 막는 것은 규칙이 아니라 규칙이 생긴 장면**이다.
  *"사용자가 두 번 같은 지적을 했다"*, *"리더가 `grep -c` 결과를 근거로 잘못된 지적을 냈다"* 처럼
  **구체적 사건**으로 쓴다. *"개선함"* 같은 요약은 쓰지 마라.

⚠ **기존 행을 고치지 마라.** 판정이 뒤집혔으면 **새 행을 추가**하고 사유에
*"§X 를 개정한다"* 로 죽은 절을 이름으로 지목한다(판정 기록 규율).

### 3.2 `.claude/skills/*/SKILL.md`

- 규칙은 **판정 가능한 문장**으로. *"주의한다"* 가 아니라 *"…이면 …한다"*.
- **금지 규칙에는 «대신 무엇을»** 을 붙인다. 막기만 하면 다음 사람이 다른 길로 같은 사고를 낸다.
- 절을 새로 만들면 **번호를 부여**하고 CLAUDE.md 변경 이력에서 그 번호로 가리킨다.
- 어느 스킬인지 헷갈리면: 검증=`union-fact-check` · 디자인=`union-design-system` ·
  프론트=`union-webapp-dev` · 백엔드=`union-backend-dev` · QA/실측=`union-qa-testing` ·
  팀 운영·판정 기록=`union-page-orchestrator`.

### 3.3 `_workspace/FOLLOWUPS.md`

각 항목은 **위치 · 경위 · 잔존 위험 · 권고 조치 · 우선순위**를 갖는다(기존 형식 유지).

⚠ **최신화의 절반은 «추가» 가 아니라 «회수» 다.**
- 해소된 항목은 **지우지 말고** 제목에 `[해소 YYYY-MM-DD]` 를 달고 **어떻게 해소됐는지 한 줄**을 남긴다.
  지우면 *"왜 없어졌지"* 가 다음 사람의 일이 된다.
- 원인 일부만 해소됐으면 **경위 문단을 고쳐** 남은 위험만 남긴다. **낡은 근거를 남기지 마라** —
  그것이 `#10` 사고다.
- 지표를 철회했으면 **그 지표에서 파생된 수치까지** 회수한다.

### 3.4 `_workspace/0X_*.md`

- 헤더의 `최종 수정` 을 갱신한다.
- **판정은 산출물에 두고 메시지는 그것을 가리킨다.** 대화에만 있는 판정은 다음 세션에 없다.
- 회차가 늘면 기존 절을 덮어쓰지 말고 **회차를 명시해 덧붙인다**.

### 3.5 `README.md`

실행법·디렉터리 구조·배포 방식이 **실제로 바뀐 경우에만** 고친다.
⚠ 현재 `create-next-app` 기본 문서 상태다. 손보려면 **그것 자체가 하나의 작업**이니
이 스킬 안에서 즉흥적으로 새로 쓰지 말고 사용자에게 범위를 물어라.

### 3.6 `AGENTS.md` — 손대지 마라

`next dev` 가 **자동 생성·재삽입**하는 블록이다(`BEGIN:nextjs-agent-rules`).
지워도 다시 생기고, 고치면 다음 실행에 덮어쓰인다.

### 3.7 메모리

`~/.claude/projects/-Users-koscom-IdeaProjects-koscomlabor/memory/`

- **코드·문서에 적을 자리가 있는 것은 메모리에 넣지 마라.**
- 넣을 것: 사용자의 작업 방식 선호, 도구·환경의 함정, 외부 자원 위치.
- 기존 파일과 겹치면 **새로 만들지 말고 그 파일을 고친다.**
- `MEMORY.md` 에 한 줄 포인터를 추가한다(내용을 넣지 마라).

## 4. 쓰지 않는 것

| 쓰지 않을 것 | 이유 |
|---|---|
| 코드·git 이 이미 말하는 것 | 파일 목록, 함수 이름, 커밋 요약 — 문서가 낡을 이유만 늘린다 |
| 이번 대화에서만 의미 있는 것 | *"세 번째 시도에서 됐다"* 는 다음 사람에게 정보가 아니다 |
| «개선했다», «최적화했다» | 판정 불가. **무엇이 어떻게 달라졌는지 수치나 조건**으로 쓴다 |
| 우리 작업 사정 | *"시간이 없어 …"* — 조합원용 문안이든 내부 문서든 마찬가지다(§5.3 정신) |
| 확인하지 않은 상태 | *"아마 해소됐을 것"* → 확인하거나, **확인하지 않았다고 쓴다** |

## 5. 절차

1. **입력 수집**(§1). 메모리 → git log → status → 현행 문서 순으로 **읽는다.**
2. **사실 목록화.** 이번 구간에서 새로 정해진 것·뒤집힌 것·미해결로 남은 것을 뽑는다.
3. **배치 판정**(§2). 각 항목에 갈 곳을 하나씩 정한다. **두 곳이면 하나를 버린다.**
4. **회수 먼저, 추가 나중.** FOLLOWUPS 해소·판정 뒤집힘부터 처리한다.
   낡은 기록이 남은 채 새 기록이 붙으면 **모순된 두 진술**이 된다.
5. **쓴다.** 형식은 §3.
6. **검산.**
   - `CLAUDE.md` 변경 이력에 추가한 행의 **대상 파일이 실제로 바뀌었는가**(`git diff --name-only`)
   - 스킬에 적은 절 번호가 **본문에 실제로 존재하는가**
   - FOLLOWUPS 의 `[해소]` 항목이 **정말 해소됐는가**(코드/실측으로 확인)
   - 문서끼리 **같은 사실을 다르게 말하지 않는가**
7. **커밋**(§6).

## 6. 커밋

문서 변경은 **코드와 분리해 커밋한다** — 나중에 *"이 규칙이 언제 왜 생겼나"* 를 찾을 때
코드 diff 에 섞여 있으면 못 찾는다.

```
docs: <무엇을 최신화했는지 한 줄>

<왜 지금 이 기록이 필요한지 — 어떤 사건이 있었는지>
<회수한 것(해소·철회)과 추가한 것을 나눠 적는다>
```

⚠ **`_workspace/` 산출물만 바뀐 경우에도 커밋한다.** 검증 이력은 감사 추적이다.
⚠ 푸시는 사용자가 요청했거나 이미 그 흐름일 때만. 기본 브랜치면 먼저 확인한다.

## 7. 판정이 서면 물어라

다음은 **혼자 정하지 않는다:**

- 사용자가 지정한 문면을 문서에서 바꾸는 것
- 검증 승인된 콘텐츠의 사실 진술을 고치는 것
- `README.md` 를 새로 쓰는 것(§3.5)
- FOLLOWUPS 항목을 **삭제**하는 것(해소 표기가 아니라 삭제)
