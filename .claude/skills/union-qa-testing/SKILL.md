# Union QA Testing — 통합 정합성 검증 방법론

각 부분이 따로 보면 정상인데 연결하면 깨지는 **경계면 버그**를 잡는 것이 QA의 핵심이다. 정적으로 파일 하나씩 읽는 리뷰로는 못 잡는다 — 반드시 경계면의 양쪽 코드를 동시에 열어 계약(shape, 경로, 이름)을 비교한다.

## 1. 검증 우선순위

1. **통합 정합성** (최우선) — 경계면 불일치가 런타임 에러의 주요 원인
2. **기능 스펙 준수** — 요구사항·디자인 스펙 대비 구현 확인
3. **접근성** — 대비, 키보드, 대체텍스트, 시맨틱 마크업
4. **빌드/타입/린트** — 통과는 전제조건일 뿐, 정상 동작의 증거가 아니다

## 2. 통합 정합성 체크리스트 (교차 비교)

각 항목은 "존재 확인"이 아니라 **양쪽 대조**다. 왼쪽과 오른쪽을 같이 열어 비교한다:

| 검증 대상 | 생산자 (왼쪽) | 소비자 (오른쪽) | 확인 내용 |
|----------|-------------|---------------|----------|
| 라우팅 | `app/` 하위 page 파일 경로 | 코드 내 모든 `href`, `router.push`, `redirect` | 모든 링크가 실존 경로와 매칭. route group `(group)`은 URL에서 제거됨을 반영 |
| 콘텐츠 스키마 | `content/` 파일 frontmatter 필드 | 콘텐츠를 읽는 컴포넌트/함수의 타입 | 필드명·옵셔널 여부 일치. snake_case↔camelCase 혼용 여부 |
| API 응답 (있는 경우) | route handler의 `NextResponse.json()` shape | 호출측 `fetch` 제네릭 타입 | 래핑(`{items:[]}`) unwrap 여부, 즉시응답 vs 최종결과 구분 |
| 디자인 토큰 | 스펙의 토큰 정의 | Tailwind 설정/CSS 변수/클래스 사용처 | 토큰 값 일치, 스펙에 없는 임의 색상·크기 사용 여부 |
| 상태 분기 | 상태 값 정의(타입/상수) | `if (status === "...")` 분기들 | 분기의 값이 실제 도달 가능한 상태인지, 죽은 분기·무단 상태 없는지 |

**타입 우회 탐지**: `grep -rn "as any\|as unknown\|@ts-ignore\|@ts-expect-error" --include="*.ts" --include="*.tsx"` — 발견된 각 지점은 컴파일러가 못 지키는 경계면이므로 수동 교차 비교 대상이다.

## 3. 접근성 검사

- **대비**: 구현물에서 실제 사용된 텍스트/배경 색 조합을 추출하여 검사 스크립트로 확인한다:
  `node .claude/skills/union-design-system/scripts/check-contrast.mjs "#fg:#bg" ...`
  기준: 본문 4.5:1 미만은 실패, 7:1 미만은 경고(스펙 목표 미달)로 리포트.
- **시맨틱 마크업**: 제목 레벨 순서(h1→h2→h3 건너뜀 없음), `<button>` vs `<a>` 용도 구분(이동은 a, 동작은 button), landmark(`main`, `nav`, `footer`).
- **이미지**: 모든 `<img>`/`Image`에 의미 있는 `alt` (장식 이미지는 `alt=""`).
- **키보드**: 클릭 핸들러가 있는 비대화형 요소(`div onClick`) 탐지 — 키보드로 도달 불가. `:focus-visible` 스타일 존재 확인.
- **터치 대상**: 버튼·링크 44×44px 미만 여부.

## 4. 빌드·정적 검사

```bash
npx tsc --noEmit      # 타입 검사
npm run lint          # 린트
npm run build         # 빌드
```

실패 시 로그 원문을 리포트에 첨부한다. 통과해도 2절의 교차 비교를 생략할 근거가 되지 않는다 — 타입 캐스팅으로 우회된 불일치는 빌드가 잡지 못한다.

## 5. Incremental QA 운영

- 전체 완성 후 1회가 아니라 **모듈 완성 직후마다** 해당 모듈 + 그 모듈이 맞닿는 경계면을 검증한다. 초기 불일치가 후속 모듈로 전파되기 전에 잡는 것이 수정 비용을 최소화한다.
- 재검증(회귀) 시: 이전 리포트의 실패 항목을 먼저 확인하고, 수정이 새 경계면 문제를 만들지 않았는지 수정 파일의 인접 경계면을 재검사한다.

## 5.5 실측 규율 — 픽셀을 재는 검증

레이아웃·점유율·잘림처럼 **숫자를 재는 검증**은 측정 자체가 틀릴 수 있다. 아래는 이 프로젝트에서 실제로 값을 치르고 얻은 규칙이다.

### 측정 환경표 — 재기 전에 먼저 찍는다

숫자를 재기 전에 **환경이 참값을 만들 수 있는지** 확인한다. 다음을 리포트 고정 항목으로 남긴다:

| 항목 | 왜 |
|------|-----|
| **`innerWidth − documentElement.clientWidth`** | **0이 아니면 스크롤바가 자리를 먹는 데스크톱 컨텍스트다.** 모바일은 오버레이라 0 |
| `navigator.maxTouchPoints` · `(pointer: coarse)` | 터치 에뮬레이션 여부. `setViewportSize`만으로는 안 켜진다 — `hasTouch`/`isMobile`은 **컨텍스트 생성 시점 옵션**이라 새 컨텍스트가 필요하다 |
| 기준 요소의 실측 rect | 그 뷰포트에서 나와야 하는 값과 대조 (예: `w-full aspect-[4/5]` 라면 `328×410`) |
| `BUILD_ID` + 대상 파일 sha256 (**측정 전후**) | 측정 중 빌드가 교체되면 결과가 무효다 |

**환경표가 기대와 다르면 그 위의 숫자를 전부 버린다.** 보정해서 쓰는 경우(예: 스크롤바 폭만큼 뷰포트를 넓혀 참 콘텐츠 폭을 복원) **보정했다는 사실과 근거를 리포트에 명시한다.** 그때도 기준 요소 rect 검산은 건너뛰지 않는다.

### 종횡비 검산 — 그리고 그것이 못 잡는 것

측정값이 CSS상 나올 수 있는 값인지 판정한다. `CSS-IMPOSSIBLE`이면 **구현이 아니라 측정을 의심**한다.

⚠ **종횡비는 종횡비 오염만 잡는다.** 폭이 줄면 높이도 비례해 줄므로 **폭 오염은 비율이 그대로다** — `313×391.3`도 `328×410`도 똑같이 `0.8`이다. **폭 오염은 위 환경표의 `innerWidth − clientWidth`로만 잡힌다.** 두 검산은 서로를 대신하지 못한다.

### 빌드 동결

- 측정 대상 빌드를 **고정하고**, 측정이 끝날 때까지 개발자가 코드를 건드리지 않는다. 측정 전후 해시가 다르면 그 회차는 무효다
- 이 프로젝트는 `output: "standalone"`이다. **`next start`를 쓰지 않는다** — 정적 자산을 서빙하지 않아 레이아웃이 축소되고 잘못된 값이 나온다. 측정 전 **정적 자산 전수 200**을 확인한다
- 포트·오리진 제약이 있으면(예: 지도 API 키가 특정 오리진만 허용) **남의 프로세스를 죽이지 말고** 우회한다. 요청을 자기 빌드로 되돌려 채우면 오리진은 유지하면서 바이트는 동결 빌드를 쓸 수 있다

### 관측이 기대와 다를 때 — 양방향으로 의심한다

**한쪽으로만 기울면 두 종류의 오답이 생긴다.**

| 잘못 | 실제 사례 |
|------|----------|
| 결함을 **환경 탓**으로 닫음 | 1280px 박스가 모바일 비율로 나온 것을 "측정 환경 결함"으로 철회 → 프로덕션에서 같은 증상 관측 → **철회를 철회** |
| 측정 조건 문제를 **구현 결함**으로 올림 | 레이아웃이 안정되기 전에 기준을 잡아 스크롤이 어긋난 것을 결함으로 보고 |

**판정 순서**: ① 그 값이 CSS상 가능한가 → ② 측정 조건이 그 값을 만들 수 있는가 → ③ 그래도 남으면 구현 결함이다. **환경을 의심하되, 의심을 결론으로 삼기 전에 그 환경에서 참값이 나올 수 있는지 실제로 확인한다.**

### 판정선을 문장으로 고정한다

"기능이 있는가"가 아니라 **"최악 조건에서 성립하는가"**로 쓴다. 완화 수단은 **위험이 최대인 순간에 작동해야** 완화다 — 평상시에만 보이는 안내는 없는 것과 같다.

예: *"문구가 존재하는가"* ✗ → *"세로 점유 85.4% 지점에서 문구 rect가 뷰포트 안인가"* ✓

**최악 지점은 눈으로 찾지 말고 전 구간을 격자로 스윕해 최댓값을 찾는다.** 그리고 **분모·분자의 정의를 리포트에 적는다** — 정의가 다르면 회차 간 비교가 성립하지 않는다.

### 사실 주장을 하는 문구는 참·거짓을 판정한다

안내 문구가 동작을 주장하면(예: *"지도 위나 아래 빈 곳을 쓸어 주세요"*) **그 주장이 참인지 확인한다.** 문구가 보이는 것과 그 말이 맞는 것은 다르고, **틀린 안내는 없느니만 못하다.** 환경 제약으로 확인할 수 없으면 **미검증으로 분리하고 통과로 적지 않는다.**

## 6. 리포트 형식

`_workspace/04_qa_report.md`에 작성한다. **미검증 항목을 통과로 표시하지 않는다** — 통과/실패/미검증 3분류를 유지한다:

```markdown
# QA 리포트: {검증 대상} ({회차})

## 요약: 통과 N | 실패 N | 미검증 N

## 실패 항목
| # | 분류 | 위치 | 내용 | 수정 방법 |
|---|------|------|------|----------|
| 1 | 라우팅 | src/components/Nav.tsx:23 | href="/notice"인데 실제 경로는 /notices | href를 /notices로 수정 |

## 통과 항목
{검증한 것만. 무엇을 어떻게 확인했는지 한 줄씩}

## 미검증 항목
{항목 + 사유 (예: 실행 환경 제약)}
```

실패 항목은 반드시 `파일:라인` + 구체적 수정 방법을 포함한다. "라우팅이 이상함" 수준의 리포트는 재작업을 유발한다.
