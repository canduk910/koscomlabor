# Union QA Testing — 통합 정합성 검증 방법론

각 부분이 따로 보면 정상인데 연결하면 깨지는 **경계면 버그**를 잡는 것이 QA의 핵심이다. 정적으로 파일 하나씩 읽는 리뷰로는 못 잡는다 — 반드시 경계면의 양쪽 코드를 동시에 열어 계약(shape, 경로, 이름)을 비교한다.

## 1. 검증 우선순위

1. **통합 정합성** (최우선) — 경계면 불일치가 런타임 에러의 주요 원인
2. **기능 스펙 준수** — 요구사항·디자인 스펙 대비 구현 확인
3. **접근성** — 대비, 키보드, 대체텍스트, 시맨틱 마크업
4. **빌드/타입/린트** — 통과는 전제조건일 뿐, 정상 동작의 증거가 아니다

## 2. 통합 정합성 체크리스트 (교차 비교)

각 항목은 "존재 확인"이 아니라 **양쪽 대조**다. 왼쪽과 오른쪽을 같이 열어 비교한다:

| 검증 대상 | 생산자 (왼쪽) | 소비자 (오른쪽) | 확인 내용 |
|----------|-------------|---------------|----------|
| 라우팅 | `app/` 하위 page 파일 경로 | 코드 내 모든 `href`, `router.push`, `redirect` | 모든 링크가 실존 경로와 매칭. route group `(group)`은 URL에서 제거됨을 반영 |
| 콘텐츠 스키마 | `content/` 파일 frontmatter 필드 | 콘텐츠를 읽는 컴포넌트/함수의 타입 | 필드명·옵셔널 여부 일치. snake_case↔camelCase 혼용 여부 |
| API 응답 (있는 경우) | route handler의 `NextResponse.json()` shape | 호출측 `fetch` 제네릭 타입 | 래핑(`{items:[]}`) unwrap 여부, 즉시응답 vs 최종결과 구분 |
| 디자인 토큰 | 스펙의 토큰 정의 | Tailwind 설정/CSS 변수/클래스 사용처 | 토큰 값 일치, 스펙에 없는 임의 색상·크기 사용 여부 |
| 상태 분기 | 상태 값 정의(타입/상수) | `if (status === "...")` 분기들 | 분기의 값이 실제 도달 가능한 상태인지, 죽은 분기·무단 상태 없는지 |

**타입 우회 탐지**: `grep -rn "as any\|as unknown\|@ts-ignore\|@ts-expect-error" --include="*.ts" --include="*.tsx"` — 발견된 각 지점은 컴파일러가 못 지키는 경계면이므로 수동 교차 비교 대상이다.

## 3. 접근성 검사

- **대비**: 구현물에서 실제 사용된 텍스트/배경 색 조합을 추출하여 검사 스크립트로 확인한다:
  `node .claude/skills/union-design-system/scripts/check-contrast.mjs "#fg:#bg" ...`
  기준: 본문 4.5:1 미만은 실패, 7:1 미만은 경고(스펙 목표 미달)로 리포트.
- **시맨틱 마크업**: 제목 레벨 순서(h1→h2→h3 건너뜀 없음), `<button>` vs `<a>` 용도 구분(이동은 a, 동작은 button), landmark(`main`, `nav`, `footer`).
- **이미지**: 모든 `<img>`/`Image`에 의미 있는 `alt` (장식 이미지는 `alt=""`).
- **키보드**: 클릭 핸들러가 있는 비대화형 요소(`div onClick`) 탐지 — 키보드로 도달 불가. `:focus-visible` 스타일 존재 확인.
- **터치 대상**: 버튼·링크 44×44px 미만 여부.

## 4. 빌드·정적 검사

```bash
npx tsc --noEmit      # 타입 검사
npm run lint          # 린트
npm run build         # 빌드
```

실패 시 로그 원문을 리포트에 첨부한다. 통과해도 2절의 교차 비교를 생략할 근거가 되지 않는다 — 타입 캐스팅으로 우회된 불일치는 빌드가 잡지 못한다.

## 5. Incremental QA 운영

- 전체 완성 후 1회가 아니라 **모듈 완성 직후마다** 해당 모듈 + 그 모듈이 맞닿는 경계면을 검증한다. 초기 불일치가 후속 모듈로 전파되기 전에 잡는 것이 수정 비용을 최소화한다.
- 재검증(회귀) 시: 이전 리포트의 실패 항목을 먼저 확인하고, 수정이 새 경계면 문제를 만들지 않았는지 수정 파일의 인접 경계면을 재검사한다.

## 5.5 실측 규율 — 픽셀을 재는 검증

레이아웃·점유율·잘림처럼 **숫자를 재는 검증**은 측정 자체가 틀릴 수 있다. 아래는 이 프로젝트에서 실제로 값을 치르고 얻은 규칙이다.

### 측정 환경표 — 재기 전에 먼저 찍는다

숫자를 재기 전에 **환경이 참값을 만들 수 있는지** 확인한다. 다음을 리포트 고정 항목으로 남긴다:

| 항목 | 왜 |
|------|-----|
| **`innerWidth − documentElement.clientWidth`** | **0이 아니면 스크롤바가 자리를 먹는 데스크톱 컨텍스트다.** 모바일은 오버레이라 0 |
| `navigator.maxTouchPoints` · `(pointer: coarse)` | 터치 에뮬레이션 여부. `setViewportSize`만으로는 안 켜진다 — `hasTouch`/`isMobile`은 **컨텍스트 생성 시점 옵션**이라 새 컨텍스트가 필요하다 |
| 기준 요소의 실측 rect | 그 뷰포트에서 나와야 하는 값과 대조 (예: `w-full aspect-[4/5]` 라면 `328×410`) |
| `BUILD_ID` + 대상 파일 sha256 (**측정 전후**) | 측정 중 빌드가 교체되면 결과가 무효다 |
| **정적 자산 해시**(또는 CSS 바이트 수, **측정 전후**) | 서버와 자산이 **따로 갈리는 구간**이 실재한다. 구 서버 + 신 자산은 **양쪽 다 정상으로 보이면서 조합만 틀리고, `BUILD_ID` 대조로도 안 잡힌다** |
| **`getComputedStyle(document.documentElement).fontSize`** | **이 프로젝트의 루트는 12px 이다**(`html{font-size:75%}`) — 모든 `rem` 토큰이 ×0.75 다. **16px 을 가정한 개산은 전부 틀린다.** 텍스트 확대 검증은 32px 에서 돈다. ⚠ **인라인으로 바꿔 재고 지우지 않으면 이후 측정이 통째로 오염된다**(§5.8.4) |
| **브라우저 탭의 라우트 잔존** | 브라우저는 공유 자원이라 포트 규율만으로 못 막는다. 다른 세션이 걸어 둔 라우트가 남아 있을 수 있다 — **새 탭에서 시작한다** |

**환경표가 기대와 다르면 그 위의 숫자를 전부 버린다.** 보정해서 쓰는 경우(예: 스크롤바 폭만큼 뷰포트를 넓혀 참 콘텐츠 폭을 복원) **보정했다는 사실과 근거를 리포트에 명시한다.** 그때도 기준 요소 rect 검산은 건너뛰지 않는다.

### 종횡비 검산 — 그리고 그것이 못 잡는 것

측정값이 CSS상 나올 수 있는 값인지 판정한다. `CSS-IMPOSSIBLE`이면 **구현이 아니라 측정을 의심**한다.

★★ **폭 오염은 «폭»만 틀리게 하지 않는다**(2026-08-27 추가 · 상세는 **§5.8.1**).
스크롤바가 줄인 폭이 조상 요소의 **`flex-wrap` 임계**를 넘기면 **줄바꿈이 일어나 높이가 계단식으로 바뀐다.**
실제로 스크롤바 15px 하나가 **높이 +50px** 을 만들어 «첫 화면 여유» 판정을 **참값의 4분의 1**로 냈다.
→ **세로 측정에도 이 환경표를 적어라.** 이 항목을 «가로 측정 전용»으로 두지 마라.

⚠ **종횡비는 종횡비 오염만 잡는다.** 폭이 줄면 높이도 비례해 줄므로 **폭 오염은 비율이 그대로다** — `313×391.3`도 `328×410`도 똑같이 `0.8`이다. **폭 오염은 위 환경표의 `innerWidth − clientWidth`로만 잡힌다.** 두 검산은 서로를 대신하지 못한다.

### 빌드 동결

- 측정 대상 빌드를 **고정하고**, 측정이 끝날 때까지 개발자가 코드를 건드리지 않는다. 측정 전후 해시가 다르면 그 회차는 무효다
- 이 프로젝트는 `output: "standalone"`이다. **`next start`를 쓰지 않는다** — 정적 자산을 서빙하지 않아 레이아웃이 축소되고 잘못된 값이 나온다. 측정 전 **정적 자산 전수 200**을 확인한다
- 포트·오리진 제약이 있으면(예: 지도 API 키가 특정 오리진만 허용) **남의 프로세스를 죽이지 말고** 우회한다. 요청을 자기 빌드로 되돌려 채우면 오리진은 유지하면서 바이트는 동결 빌드를 쓸 수 있다

### 관측이 기대와 다를 때 — 양방향으로 의심한다

**한쪽으로만 기울면 두 종류의 오답이 생긴다.**

| 잘못 | 실제 사례 |
|------|----------|
| 결함을 **환경 탓**으로 닫음 | 1280px 박스가 모바일 비율로 나온 것을 "측정 환경 결함"으로 철회 → 프로덕션에서 같은 증상 관측 → **철회를 철회** |
| 측정 조건 문제를 **구현 결함**으로 올림 | 레이아웃이 안정되기 전에 기준을 잡아 스크롤이 어긋난 것을 결함으로 보고 |

**판정 순서**: ① 그 값이 CSS상 가능한가 → ② 측정 조건이 그 값을 만들 수 있는가 → ③ 그래도 남으면 구현 결함이다. **환경을 의심하되, 의심을 결론으로 삼기 전에 그 환경에서 참값이 나올 수 있는지 실제로 확인한다.**

### 판정선을 문장으로 고정한다

"기능이 있는가"가 아니라 **"최악 조건에서 성립하는가"**로 쓴다. 완화 수단은 **위험이 최대인 순간에 작동해야** 완화다 — 평상시에만 보이는 안내는 없는 것과 같다.

예: *"문구가 존재하는가"* ✗ → *"세로 점유 85.4% 지점에서 문구 rect가 뷰포트 안인가"* ✓

**최악 지점은 눈으로 찾지 말고 전 구간을 격자로 스윕해 최댓값을 찾는다.** 그리고 **분모·분자의 정의를 리포트에 적는다** — 정의가 다르면 회차 간 비교가 성립하지 않는다.

### 런타임에 위치가 정해지는 요소는 표본 집합으로 잰다

좌표·크기가 사용자 입력이나 기기 상태로 정해지는 요소(내 위치 표시, 동적 삽입 배지 등)는 **한 점 측정이 그 점에 대해서만 말한다.** *"겹침 0"* 이라고 적으면 다음 사람은 전 구간을 읽지만, 실제로는 모킹한 좌표 하나에서만 확인된 것이다.

**대표 위치를 4~5점 정해 그중 최솟값을 회차 기록으로 남긴다.** 고를 때는 *"무엇과 가까워질 수 있는가"* 로 고른다 — 각 이웃 요소마다 한 점씩, 그리고 **실사용에서 가장 흔한 위치**를 반드시 포함한다.

**가변 요소는 그 치수도 함께 기록한다.** 라벨 문자열이 바뀌면 폭이 바뀌고, 그러면 이전 회차의 간격 값과 비교가 성립하지 않는다.

### 조건문은 그것을 발동시킬 절차와 짝이어야 한다

*"X가 관측되면 올려라"* 같은 재개·승격 조건을 쓸 때는 **관측 설계가 실제로 X를 만들 수 있는지** 먼저 확인한다. 만들 수 없으면 그 조건은 조건이 아니라 **통과 사유로만 쓰인다** — 영원히 발동하지 않으므로 항상 참으로 읽힌다.

이 프로젝트에서 실제로 그랬다: *"실교차가 관측되면 재개한다"* 를 종결 조건으로 걸었는데, 측정이 모킹 좌표 한 점에서만 이뤄져 **그 조건이 발동할 경로가 없었다.**

### 사실 주장을 하는 문구는 참·거짓을 판정한다

안내 문구가 동작을 주장하면(예: *"지도 위나 아래 빈 곳을 쓸어 주세요"*) **그 주장이 참인지 확인한다.** 문구가 보이는 것과 그 말이 맞는 것은 다르고, **틀린 안내는 없느니만 못하다.** 환경 제약으로 확인할 수 없으면 **미검증으로 분리하고 통과로 적지 않는다.**

## 6. 리포트 형식

`_workspace/04_qa_report.md`에 작성한다. **미검증 항목을 통과로 표시하지 않는다** — 통과/실패/미검증 3분류를 유지한다:

```markdown
# QA 리포트: {검증 대상} ({회차})

## 요약: 통과 N | 실패 N | 미검증 N

## 실패 항목
| # | 분류 | 위치 | 내용 | 수정 방법 |
|---|------|------|------|----------|
| 1 | 라우팅 | src/components/Nav.tsx:23 | href="/notice"인데 실제 경로는 /notices | href를 /notices로 수정 |

## 통과 항목
{검증한 것만. 무엇을 어떻게 확인했는지 한 줄씩}

## 미검증 항목
{항목 + 사유 (예: 실행 환경 제약)}
```

실패 항목은 반드시 `파일:라인` + 구체적 수정 방법을 포함한다. "라우팅이 이상함" 수준의 리포트는 재작업을 유발한다.

## 5.6 측정 환경 — «재기 전에 잴 수 있는 상태인지» 먼저 확인한다 (2026-08-25 신설)

§5.5 의 측정 환경표에 **다음 두 줄을 추가한다. 이 확인 없이 나온 «동작 안 함» 판정은 근거가 되지 않는다.**

| 항목 | 명령 | 통과 조건 |
|---|---|---|
| 문서 가시성 | `document.visibilityState` | `"visible"` |
| 프레임 발화 | `requestAnimationFrame` 콜백이 1.5초 안에 오는가 | 온다 |

> **장면(2026-08-23)**: 로드뷰 시트 드래그 검증에서 *"`ResizeObserver → setSize` 가 한 번도
> 호출되지 않는다"* 는 측정이 나왔다. **없는 결함을 있다고 판정할 뻔했다.**
> 대조로 붙인 자체 `ResizeObserver` 도 안 울려서 **코드가 아니라 환경**임이 드러났다 —
> 탭이 `visibilityState: "hidden"` 이라 **rAF 와 ResizeObserver 가 아예 돌지 않았다.**
> 보이는 브라우저로 옮기니 전부 통과했다.

⚠ **rAF·`ResizeObserver`·`IntersectionObserver`·애니메이션·스크린샷**이 걸린 검증은 특히 그렇다.
스크린샷이 **빈 흰 프레임**으로 오면 그것부터 의심하라.

### 회귀 축 하나 추가 — 열이 늘면 «확대 배율» 을 다시 잰다

**표에 열을 추가하거나 고정 폭을 줄였으면 텍스트 확대 200% 를 반드시 다시 잰다.**
기본 배율만 보고 통과시키면 안 된다.

> **장면(2026-08-25)**: 결의대회 순서 표를 2열 → 3열로 바꾸고 **360·390·1280px 기본 배율에서
> 넘침 0** 을 확인해 배포했다. 나중에 200% 로 재 보니 **전체 넘침 203px** 중
> **표 기여가 134px** 이었다(표를 숨겨 69px 로 떨어지는 것으로 기여분을 분리했다).
> 열 폭은 고정인데 글자만 2배가 되고, `break-keep` 이 걸린 한국어는 갈 곳이 없다.

**기여분 분리법**: 의심 요소를 `display:none` 으로 감췄다 되돌리며
`documentElement.scrollWidth - clientWidth` 의 차이를 본다. **«무엇이 얼마나» 를 수치로 가른다.**

## 5.7 값·방법·기준 / 낡은 «프로세스» / 높이 축 (2026-08-26 신설)

§5.5·§5.6 이 **«환경이 참값을 만들 수 있는가»** 를 다뤘다면, 이 절은 **측정이 정확했는데도 오독된 경로**를 다룬다.

### 측정값은 «값 + 방법 + 기준» 이 한 벌이다

- **값만 적지 마라. «어떻게 쟀나(방법)» 와 «어디를 기준으로 쟀나(슬롯·분모)» 를 같은 줄에 적는다.** 셋 중 하나가 빠지면 다음 사람이 그 값을 다른 뜻으로 인용한다.
- `min-content` · `표시 폭` · `슬롯` · `여백` 은 **구현이 여럿인 낱말**이다. 이름만 쓰지 말고 괄호로 방법을 적는다 — 예: `` `scrollWidth`(width:0 상태) ``.
- **판정**: 텍스트 최소 폭의 이 프로젝트 표준은 **`width:0` 요소의 `scrollWidth`** 다. `width:min-content` 요소의 rect 로 재지 마라 — 명세상 `overflow-wrap: break-word` 는 내재 크기에 영향을 주지 않아 **«스펙상 맞는 값»이지만 «질문에 대한 답»이 아니다.**
- **구현 전 사전 실측은 자리가 미정이라 슬롯도 미정이다.** 후보 슬롯을 **전부 재거나**, 표 머리에 **«어느 슬롯 기준인지»를 명시**한다. 명시 없는 사전 실측표는 인용 금지.

> **장면(2026-08-26)**: 디자이너와 QA 가 `min-content` 라는 **같은 이름으로 다른 양**을 쟀다 —
> `width:0` 의 `scrollWidth`(311 → 31) 대 `width:min-content` 의 rect(311.1 → **311.1**).
> **`break-keep` 단독 열에서는 두 값이 같아**(311↔311.1) 아무도 눈치채지 못했고 **`+break-words` 열에서만 갈렸다.**
> 참값(고정폭 201px 박스의 초과: 110px → 0)과 부호가 맞는 것은 전자였다 — 후자로 판정하면 **거짓 실패**가 난다.
>
> 같은 라운드에 QA 사전 실측표가 **어느 슬롯 기준인지 안 적혀**, 개발자가 **카드 «밖»(281px)에 앉은 문장에
> 카드 «안»(201px) 수치를 인용**해 *"161(320급)에서 4px 초과"* 라는 주석을 달았다. 실제 초과는 **전 구간 0** 이었다.
> 이 페이지는 같은 뷰포트에서 슬롯이 **201(카드 `p-5` 안) / 281(카드 밖)** 두 가지고, 차이는 `p-5` 양쪽 **80px** 이다.

⚠ **§5.5 와 결이 다르다.** §5.5 는 **«같은 정의로 다른 값»**(스크롤바 오염 · 81.5% vs 85.4%)이고, 이것은 **«다른 정의를 같은 이름으로 불렀다»** 다. **두 사람 다 자기 측정은 정확했으므로 환경표로는 안 잡힌다.**

### 빌드 완료 ≠ 배포 완료 — 낡은 «파일» 이 아니라 낡은 «프로세스»

**`npm run start` 는 `EADDRINUSE` 로 죽어도 종료코드 `0` 을 낸다. 종료코드 0 을 «떴다» 로 읽지 마라.** 띄우기 전에 포트가 비었는지 확인하고, 안 비었으면 정지 후 **해제를 확인하고** 띄운다. 그리고 측정 전에 아래 **3종을 전부** 통과시킨다:

| # | 확인 | 방법 | 통과 조건 |
|---|------|------|----------|
| ① | 내가 띄운 프로세스가 그 포트를 잡았나 | `lsof -nP -iTCP:3000 -sTCP:LISTEN` | PID 가 **기동 전후로 달라졌다** · 기동 로그 `EADDRINUSE` **0건** |
| ② | **서버가 내 빌드를 내보내나** | **서버 응답 HTML sha256 ↔ 디스크 프리렌더 sha256** | 동일 |
| ③ | 자산이 다 붙나 | 정적 자산 **전수** 요청 | 전부 200 |

★ **②가 가장 강하다.** `BUILD_ID` 대조는 서버가 **자기 값**을 내므로 자기모순을 못 잡지만, sha256 대조는 **두 출처(프로세스 ↔ 디스크)를 맞대므로** 잡는다.

> **장면(2026-08-26)**: 리더가 1차 재빌드 서버(PID 78347)를 정지하지 않은 채 2차 재빌드 후 다시 띄웠다.
> `EADDRINUSE` 로 즉시 죽었는데 **종료코드가 `0`** 이라 실패 신호가 없었고, `curl` 은 **낡은 서버가 응답해 성공**했다.
> 그래서 문면 대조에서 **구 문면이 렌더에 나왔다**(`투쟁조끼` 6회 · 구 캡션 2회 · 구 산문 2회).
> 증상은 **CSS 하나만 404** 였고 **JS 청크 9개는 전부 200** — **«양쪽 다 정상으로 보이면서 조합만 틀린»** 상태다.
> 디스크 `BUILD_ID` 는 새 값이었다. 낡은 것은 «파일»이 아니라 **«프로세스»** 였고,
> 그 서버는 **자기 옛 `BUILD_ID` 를 그대로 들고 있어 자기 기준으로는 일관적**이었다.

이는 §5.5 환경표의 **«구 서버 + 신 자산»** 항목을 이 경로로 확장한 것이다 — 그때의 믿음은 *"어제 서버가 살아 있었다"* 였고, 이번은 **«내가 방금 띄웠다고 믿은 서버가 실은 안 떴다»** 다. **믿음의 출처가 다르므로 확인 절차도 다르다.**

### 뷰포트 판정선에 «높이 축» 을 세운다

이 프로젝트 판정선에는 **폭만 있었다**(360 · 412 · 768 · 1280). **높이 판정선은 `360×640` 으로 확정한다.** 그보다 낮은 기기(`360×568`, 2016년 기기 급)를 만족시키려고 **게시 조건 문장을 깎지 않는다 — 순서가 거꾸로다.** 세로가 걸리면 문장이 아니라 **레이아웃(여백·이미지 높이)** 을 먼저 줄인다.

**«지금 통과한다» 를 «안전하다» 로 읽지 마라.** 통과 항목은 **판정선까지의 여유를 함께 적는다.** 여유가 한 자릿수 px 이면 다음 사람이 문면을 한 글자 늘릴 때 넘친다 — 그 사실이 리포트에 없으면 알 길이 없다.

> **장면(2026-08-26)**: 통과로 적힌 두 항목의 실측 여유가 **산문 7px**(min-content 194 vs 슬롯 201)과
> **데스크톱 지부명 판독 8.8px** 이었다. 후자는 `md:max-w-[560px]` 같은 **폭 상한을 두면 7.9px 로 떨어져 판독이 죽는다** —
> «폭 상한 금지» 는 취향이 아니라 **측정된 경계(560px)** 다.

### ⚠ 대조는 «두 출처 사이» 에 한다 — «두 시각 사이» 가 아니다 (2026-08-27 정정)

위 «확인 3종» 의 ②를 **«측정 전후 해시가 같은가» 로 쓰면 오탐이 난다.** 그것은 ②가 아니다.

| 쓰는 법 | 판정 |
|---|---|
| **«서버 응답 sha256 == 디스크 프리렌더 sha256»** — **같은 시각**에 두 출처를 맞댄다 | ✅ **유효.** 이것이 ②다 |
| «측정 시작 해시 == 측정 종료 해시» — **같은 출처**를 두 시각에 잰다 | ❌ **오탐.** 동결 기준으로 쓰지 마라 |

**왜 오탐인가**: Next 는 **RSC flight 페이로드에 시간에 따라 변하는 캐시 수치**를 넣는다.
**같은 빌드·같은 프로세스인데 요청 시각만 달라도 해시가 바뀐다.**

> **장면(2026-08-27)**: 측정 전후 프리렌더 해시가 `ac8a87da…` → `bdc7ec6b…` 로 갈려 **§5.5 «빌드 동결» 위반으로
> 회차를 버릴 뻔했다.** 원인을 가르니 **전체 바이트는 74,400 으로 동일**했고,
> **`<script>` 를 제거한 가시 마크업 해시는 `db81eed2…` 로 완전 일치**(29,941자)했다.
> 차이는 **RSC 페이로드 안 숫자 77자**뿐이었다(`,4608]}` → `,4256]}`).
> 그리고 ②(두 출처 대조)는 **두 시각 모두 일치**했다 — **둘이 «함께» 흔들렸을 뿐 어긋난 적이 없다.**

**빌드 동결의 참 기준** — 이 셋으로 판정한다:
1. `BUILD_ID` 불변  2. `.next/build-manifest.json` mtime 불변  3. **빌드보다 새로운 소스 파일 0건**
콘텐츠까지 비교해야 하면 **`<script>…</script>` 를 제거한 뒤 해시**한다.

#### ⚠ 오탐 모드가 둘이다 — 해시 «한 번» 값으로 판정하지 마라

| 모드 | 증상 | 대응 |
|------|------|------|
| **① RSC 캐시 수치 표류** | 같은 빌드·같은 프로세스인데 **시각이 다르면** 해시가 다르다 | «전후» 대신 **같은 시각에 두 출처**를 맞댄다 |
| **② 라이트백 중 읽기** | **빈 해시·부분 해시**가 나온다 | **2~3회 읽어 «안정»을 요구**한다 |

> **장면(2026-08-27)**: 측정 후 확인에서 디스크 프리렌더 sha256 이 **`e3b0c44298fc1c14…`** 로 나왔다.
> **파일이 사라진 줄 알았는데 74,419바이트로 멀쩡했다** — Next 응답 캐시 **라이트백 순간에 읽은 것**이다.
> 3회 재측정하니 서버 ↔ 디스크가 **3회 모두 같은 값**이었다.

★ **`e3b0c44298fc1c14…` 는 «빈 문자열»의 sha256 이다.** 이 값이 보이면 «파일이 없다»가 아니라
**«빈 것을 읽었다»를 먼저 의심하라** — 알아 두면 5초에 갈린다.

→ **②의 개정 문면**: *«서버 응답 sha256 == 디스크 프리렌더 sha256» 을 **같은 시각에, 값이 안정될 때까지 2~3회** 확인한다.*

★ **틀린 것은 «두 출처를 맞대라» 가 아니라 «같은 해시가 시간이 지나도 유지된다» 는 암묵 가정이다.**
이 프로젝트에서 «세는 방법이 질문에 안 맞는» 사례가 이것으로 **여섯 번째**다
(`grep -c` · `min-content` 정의 · 슬롯 기준 · RSC 플라이트 계수 · 텍스트 좌표 슬라이싱 · **이 건**).
★ **그중 둘이 RSC 페이로드다** — Next 산출물을 셀 때는 **`<script>` 를 먼저 지운다**를 기본값으로 삼아라.

### 해시로 «무엇이 바뀌었나» 를 답할 때 — 경로와 «코드 골격» (2026-09-01 추가)

해시는 대조에 쓰이는 순간 **값 + 방법 + 기준**이 한 벌이어야 한다는 이 절의 규칙을 그대로 받는다.

- **해시에는 «어느 파일의 어느 경로» 를 함께 적는다.** 경로 없는 해시는 **대조가 성립하지 않는다** —
  받는 쪽이 같은 대상을 재고 있는지 확인할 방법이 없다.
- ★ **«주석만 바뀌었다» 는 전체 해시로 «영원히» 못 가른다.** 주석이 바뀌면 전체 해시도 바뀌기 때문이다.
  **대신 무엇을**: `주석·빈 줄을 제거한 «코드 골격» 해시`를 함께 남긴다. 두 열(전체 / 코드만)을 나란히 적으면
  **「전체는 달라졌는데 코드만은 같다」 = 주석만 바뀌었다**가 **한 눈에 판정된다.**
- ⚠ **「번들이 바이트 동일하다」 도 같은 요구를 받는다.** 개발 서버 청크는 이름·내용이 실행마다 달라질 수 있으므로
  **어느 산출물 경로인지** 없이는 상대가 재현할 수 없다.

> **장면(2026-09-01)**: 개발자가 *「지도 번들 `79b75364`·`b7c91f5a` 바이트 동일」* 로 보고했는데
> **경로가 없어** 검증자가 대조하지 못했다(자기가 잰 청크는 `3915e8fa`… 였고 **같은 대상인지 알 방법이 없었다**).
> 그리고 *「주석만 바뀌었다」* 는 **개발자의 주장으로만 남았다** — 비교 기준(이전 시점 스냅샷)이 없어
> 검증자가 **확인할 수 없다고 적었다.** 그 자리에서 **«코드 골격» 해시 기준선**을 남기는 것으로 처방이 섰다.

## 5.8 «높이» 를 잴 때의 함정 셋 (2026-08-27 신설)

§5.7 이 높이 판정선(`360×640`)을 세운 뒤 **첫 실측에서 세 가지에 걸렸다.** 셋 다 «값»이 아니라
**«무엇이 그 값을 만드는가»** 를 잘못 본 것이다.

### 5.8.1 스크롤바 오염은 «폭» 이 아니라 «높이» 로 나타날 수 있다

§5.5 는 스크롤바가 **콘텐츠 폭**을 줄인다고 경고한다. **그 폭 감소가 «레이아웃 분기»를 넘기면
높이가 계단식으로 바뀐다.**

> **장면(2026-08-27)**: 같은 항목을 두 번 재서 **50px** 차이가 났다(548.3 vs 598.3).
> 원인은 헤더의 `flex-wrap` 이었다 — 한 줄을 유지하려면 `clientWidth ≥ 351.2px` 이 필요한데
> **스크롤바 15px 이 345 로 깎아 두 줄이 됐고, 그 아래 모든 것이 50px 내려갔다.**
> 이 프로젝트 규율대로 **실기기는 오버레이 스크롤바(0)** 이므로 **참값은 스크롤바 0 쪽**이었고,
> 오염값으로 낸 판정(«여유 14.7px»)이 **참값(64.7px)의 4분의 1** 이었다.

**규칙**:
- 세로 측정에도 **`innerWidth − clientWidth` 를 환경표에 적는다**(§5.5 는 가로 측정 항목으로만 두지 마라)
- **`flex-wrap`·`grid-auto-flow`·줄바꿈이 있는 조상 요소**가 측정 대상 «위»에 있으면,
  **그 요소가 접히는 임계 폭을 함께 잰다.** 임계 근처면 **스크롤바 0/15 두 조건을 모두** 재고
  **어느 쪽이 참값인지 명시**한다
- 같은 값이 두 번 다르게 나오면 **평균 내지 말고 원인을 갈라라.** 이번 차이는 우연이 아니라 **계단**이었다

### 5.8.2 인라인 요소의 세로 패딩은 레이아웃을 밀지 않는다

높이를 «자식 rect 합»으로 개산하면 틀린다.

> **장면(2026-08-27)**: 예측과 실측이 **두 회차 연속 정확히 3px** 갈렸다(30.1↔33.1 · 11.7↔14.7).
> 분해하니 상태 배지 `<span>` 이 **`display:inline`** 이고 `padding: 3px 9px` 인데,
> **인라인 요소의 세로 패딩은 줄 상자 높이를 늘리지 않는다.**
> `<p>` 높이는 자기 `line-height: 18px` 이 정하고, span rect 19px 는 **줄 상자를 넘치지만 밀지 않는다.**
> 예측이 배지를 **21px(패딩 포함)** 로 세어 3px 이 더해졌다.

**규칙**: 높이 개산에는 **`getBoundingClientRect()` 를 쓰지 말고 «흐름에 기여하는 값»** 을 쓴다.
인라인 요소는 **`line-height`** 가 기여하고, 세로 `padding`·`border` 는 **그리기만 하고 밀지 않는다.**
⚠ **개산과 실측이 «같은 폭으로 반복해서» 갈리면 우연이 아니다 — 계통 차이다. 원인을 찾아라.**

### 5.8.3 «실기기 가용 높이» 는 데스크톱에서 못 잰다 — 판별법이 있다

모바일 브라우저는 툴바 때문에 **레이아웃 뷰포트보다 실제 보이는 높이가 작다.** 그것을 데스크톱에서
재려고 하면 **잰 줄 알고 틀린 값을 얻는다.**

**판별법**: **`100svh` 와 `100lvh` 를 함께 찍는다.**
- **두 값이 같으면** 그 환경에는 «툴바 보임/숨김» 구분이 **없다** → **실기기 값은 못 잰다.**
  **«추정»으로 표시하고 후속으로 넘겨라.** `clientHeight`·`innerHeight`·`visualViewport.height` 가
  전부 같은 값을 내도 **그것은 «측정됐다»가 아니다**
- 갈리면 그 차이가 툴바 높이다

⚠ **못 재는 것을 «통과»로 적지 마라.** 판정선 안이면 «선언 판정선 통과 + 실기기는 미측정» 으로
**두 문장을 나눠 적는다.** 합치면 다음 사람이 «실기기에서 확인됐다» 로 읽는다.

### 5.8.4 측정 «위생» — 내가 남긴 것을 내가 다시 재지 않는다 (2026-08-27 추가)

§5.6 이 «측정 «전»에 환경을 확인하라»(`visibilityState`·rAF)를 세웠다. **같은 계열로 «측정 «후»에 내가 바꾼 것을 되돌린다»** 가 필요하다. 한 라운드에 셋에 걸렸다.

**① 잔여 스타일 — 내가 남긴 것을 내가 쟀다**

> **장면**: 절벽 위치를 이분 탐색하며 `documentElement.style.width` 를 바꿨는데 **마지막 값(320px)을 정리하지 않았다.**
> 다음 측정이 **700px 뷰포트에서 그 320px 를 재서** «헤더가 접혔다» 는 거짓 결과를 냈다.

**규칙**: 측정 함수는 **`try`/`finally` 로 자기가 바꾼 것을 되돌린다.** 그리고 **결과에 «잔여물» 을 함께 반환**해
`(없음)`·`0` 인지 **값으로** 확인한다 — «지웠다»는 **믿음이 아니라 수치**여야 한다.

★★ **범위는 인라인 스타일보다 넓다**: 주입한 `<style>` · 삽입한 프로브 요소 · 스크롤 위치 ·
**영속 상태(`localStorage`·쿠키)** 까지다. 실제로 이번에 글자 크기 슬라이더를 130% 까지 올려 재는 동안
그 값이 **`localStorage` 에 저장됐다** — 정리하지 않았으면 **이후 모든 페이지 측정이 130% 로 오염**될 뻔했다.
⚠ §5.6 이 «측정 «전» 환경이 **잴 수 있는 상태**인가»(`visibilityState`·rAF)를 세웠다면,
이것은 «환경이 **깨끗한 상태**인가» 다 — **같은 계열의 다른 축**이다. ⚠ **탐색 루프 안에서 바꾼 값은 «반환값 계산» 때 또 바뀐다** — 반환 객체를 만드는 식 안에서
DOM 을 변형하는 헬퍼를 호출하지 마라.

**② 미디어 쿼리는 «뷰포트» 기준이다 — 요소 폭을 바꿔도 안 걸린다**

> **장면**: `sm:` 반응형 복원을 확인하려고 `documentElement.style.width = '700px'` 로 재니
> **복원이 안 된 것으로 나왔다.** 미디어 쿼리는 뷰포트를 보므로 요소 폭은 무관하다.
> 실제 뷰포트를 리사이즈하니 정상이었다.

**규칙**: **반응형 분기(`sm:`·`md:`)를 검증할 때는 반드시 «뷰포트 리사이즈»** 를 쓴다.
`style.width` 트릭은 **«컨테이너 폭에만 반응하는 것»**(`flex-wrap` 임계 등)에만 쓸 수 있다. **둘을 섞지 마라.**

**③ 프록시로 판정하지 마라 — 참값을 재라**

> **장면**: «줄바꿈 = 행 높이 > 60px» 이라는 휴리스틱을 썼는데, **폭·확대에 따라 행 높이가 변해 프록시가 깨졌다.**
> 참값은 **두 자식의 `getBoundingClientRect().top` 이 다른가**다.

**규칙**: «접혔나»·«보이나»·«넘쳤나» 를 **파생 수치의 임계**로 판정하지 마라. **그 사실을 직접 말하는 값**을 찾아라
(줄바꿈 → 자식 `top` 비교 / 넘침 → `scrollWidth − clientWidth` / 판독 → 렌더 후 육안).
★ 이것은 §5.7 «세는 방법이 질문에 맞는가» 의 **측정판**이다.

## 5.9 «어디서·언제 재는가» — 판정선의 적용 범위 (2026-08-29 신설)

§5.8 까지가 «무엇이 그 값을 만드는가» 였다면, 이번 셋은 **«그 판정선이 지금 이 자리에서도 참인가»** 다.
셋 다 **«세는 방법이 질문에 안 맞는»** 계보에 속한다(§5.7 말미가 그 계보를 처음 이름 지었다).

⚠⚠ **이 계보를 «몇 번째» 로 세지 마라.** §5.7 은 «여섯 번째» 라고 적었고, 같은 라운드에
`union-fact-check` 가 **같은 계보의 사례 둘**(금지어를 «소스 전체»에서 셈 · 태그가 낀 문자열)을
**세지 않고** 추가했다 — **숫자는 적은 그 순간부터 낡는다.** 이 프로젝트는 계수 갱신 누락을 이미 겪었다.
→ **번호가 아니라 «목록» 으로 관리한다. 새 사례는 아래에 «이어 붙인다».**

| 사례 | 어디에 | 무엇을 잘못 셌나 |
|------|--------|-----------------|
| `grep -c` · `min-content` 정의 · 슬롯 기준 · RSC 플라이트 계수 · 텍스트 좌표 슬라이싱 · 해시 표류 | §5.5~§5.7 | (선행 6건) |
| **판정선이 자리를 안 가림** | **§5.9.1** | 접힐 수 «있는» 값으로 «이 자리의» 폭을 판정했다 |
| **전이 중간값** | **§5.9.2** | 값이 «안정된 시점» 이 아닌 때에 읽었다 |
| **미생성 클래스** | **§5.9.3** | 프로토타입에 **없는 여백**을 «있다» 고 세었다 |
| 금지어 계층 오선택 · 태그 낀 문자열 | `union-fact-check §5.9` | 렌더가 아닌 **주석**을 셌다 / `<wbr>` 로 갈린 문자열을 셌다 |

★ **§5.9.3 은 «새 사례» 이면서 «재발» 이다** — 같은 라운드에서 이미 만난 원인이 **다른 축**으로 다시 났다.

### 5.9.1 `width:0` 의 `scrollWidth` 판정선은 «블록 요소에서만» 참이다

`overflow-wrap: break-word`(`break-words`)는 **줄을 끊어 «그려» 주지만 min-content 기여값은 줄이지 않는다.**
그리드 트랙·표 열은 **그 기여값으로 트랙 폭을 정한다** — 그래서 **같은 요소가 블록 안에서는 통과하고
트랙 안에서는 문서를 민다.**

> **장면(2026-08-29 · 총파업 안내 페이지)**: 역명 병기 문자열이 블록 컨텍스트에서는
> `break-words` 로 **146px → 31px** 로 접혔다. 그런데 `grid-cols-[auto_1fr]` 의 `1fr` 트랙은
> **146 을 그대로 잡아** 텍스트 확대 200% 에서 문서를 **9px** 밀었다.
> 판정선(«`width:0` 의 `scrollWidth` 가 슬롯 폭 이하면 통과»)은 **틀리지 않았다 — 적용 범위 밖이었다.**

**규칙**:
- 측정 대상이 **«내용 폭으로 자기 폭을 정하는 자리» 안**이면 `width:0` 의 `scrollWidth`
  **판정선을 쓰지 마라.** (그 자리의 목록과 기전은 `union-design-system §0.8.1` 표가 갖는다 —
  여기에 두 벌로 적지 않는다. 2026-08-29 기준 **그리드 트랙·표 열·flex 아이템** 셋이다.)
- **대신 무엇을**: **실제 조판을 읽어 «그 자리의 참 슬롯 폭»을 구하고, 그 폭으로 넘침을 판정한다.**
  자리마다 찍는 값이 다르다:
  - 그리드 트랙 → **부모**의 `getComputedStyle(parent).gridTemplateColumns` (트랙 «수»와 «폭»)
  - 표 열 → 그 열 **셀 하나**의 `getBoundingClientRect().width`
  - flex 아이템 → **아이템 자신**의 `getBoundingClientRect().width`
  ⚠ 셋 다 **대상 요소 자신의 `scrollWidth` 와 비교**한다(`scrollWidth > 슬롯 폭` 이면 넘침).
  `width:0` 로 바꿔 재는 절차는 **여기서는 쓰지 않는다** — 그것이 이 절이 금지하는 바로 그 값이다.
- ⚠ **클래스 문자열을 읽어 트랙을 추론하지 마라.** 반응형 접두사(`md:` 등)가 걸려 있으면
  **소스에 적힌 열 수와 실제 조판이 다르다.** 판정 근거는 **계산된 값**이다.
- ★ **처방**(«어떤 컨텍스트에서 몇 열로 둘 것인가»)은 `union-design-system §0.8` 소관이다.
  **여기는 «어떻게 재나» 만 적는다.**

### 5.9.2 전이가 걸린 속성은 `transition-duration` 을 «넘겨» 기다린 뒤 읽는다

`focus()`·클릭·클래스 토글 **직후에 읽은 계산값은 «전이 중간값»** 일 수 있다. 중간값을 참값으로 적으면
**없는 결함이 생긴다.**

> **장면(2026-08-29)**: `:focus-visible` 아웃라인 색을 `focus()` 직후 **rAF 2회(≈32ms)** 에 읽어
> **`rgb(91,119,176)`** 이 나왔다. 스펙은 흰색이고 **400ms 뒤 참값은 `rgb(255,255,255)`** 였다.
> 원인은 **Tailwind v4 `transition-colors` 가 `outline-color` 를 포함**하고 `duration-150` 이 걸려 있던 것.
> 그대로 적었으면 *«딥블루 면 위 아웃라인 대비 미달»* 이라는 **거짓 실패**가 났다.

**규칙**:
- 색·크기·위치를 읽기 **전에** 그 속성에 **전이가 걸려 있는지 확인**한다
  (`getComputedStyle(el).transitionProperty` · `transitionDuration` · **`transitionDelay`**).
- 걸려 있으면 **대기 시간 = `transitionDelay` + `transitionDuration` + 여유 100ms** 를 계산해
  그만큼 기다린 뒤 읽는다. ⚠ **`transitionDelay` 를 빼먹지 마라** — `duration` 만 기다리면
  **지연이 걸린 전이에서는 아직 시작도 안 한 값**을 읽는다.
  ⚠ 값이 **여러 속성 목록**이면(`transitionDuration: "150ms, 300ms"`) **가장 큰 쌍**을 기준으로 한다.
- **판정**: 대기 후 **같은 값을 두 번 읽어 일치할 때만** 참값으로 적는다. 다르면 아직 전이 중이다.
  ⚠ **rAF 횟수로 대신하지 마라** — rAF 는 «프레임»을 세지 «전이 완료»를 세지 않는다.
- ⚠ **`transition-colors` 류 유틸리티가 «무엇을» 포함하는지 추측하지 마라.**
  프레임워크 버전마다 목록이 다르다 — **계산된 `transitionProperty` 를 찍어 확인**한다.
- ★ §5.6 이 «측정 «전» 환경이 **잴 수 있는** 상태인가», §5.8.4 가 «환경이 **깨끗한** 상태인가» 라면,
  이것은 **«지금 이 순간이 값이 «안정된» 시점인가»** 다 — **같은 계열의 «시간 축»** 이다.

### 5.9.3 런타임 주입 프로토타입으로 «판정선» 을 확정하지 마라 — **축을 가리지 않는다**

빌드 도구가 **소스를 훑어 CSS 를 생성**하면, 런타임에 주입한 마크업이 쓰는 유틸리티는
**그 CSS 에 없을 수 있다.** 없는 클래스는 **오류를 내지 않고 «0» 으로 그려진다** — 그래서
프로토타입은 **작아 보이고, 그 값으로 세운 예산은 산출물에서 넘친다.**

> **장면(2026-08-29)**: 디자이너의 세로 예산 예측 **173.6** vs 빌드 산출물 **188.44** = **14.84px** 차이.
> 원인은 행 간격 유틸리티가 프로토타입에서 **`row-gap: 0` 으로 그려진 것**이었다 —
> 그 클래스 사용처가 **신설 페이지 3곳뿐**이라 컴파일된 CSS 에 아예 없었다.
> **3px × (6행 사이 5곳) = 15px** 로 차이와 일치했다.
> ★★ **같은 함정을 그 라운드에서 이미 만났다**(반응형 그리드 클래스 미생성).
> 그때 **가로는 인라인 스타일로 우회해 참값을 얻었는데 «세로는 우회하지 않아»** 오차가 그대로 흘렀다 —
> **같은 원인, 다른 축. «가로만 막은 것» 이 실패다.**

**규칙**:
- **px 판정선은 «빌드 산출물»에서만 확정한다 — 가로 넘침·세로 예산·여유·절벽 전부.**
  프로토타입 값은 **«설계가 성립하는가» 까지만** 말한다.
  ⚠⚠ **이 규칙을 «세로» 로 좁혀 읽지 마라.** 기전은 «빌드 도구가 안 훑은 클래스가 오류 없이 `0` 으로
  그려진다» 이고 **축과 무관**하다. 초안이 «세로 예산» 으로 한정돼 있었는데,
  **그러면 아래 장면의 교훈(«가로만 막은 것이 실패다»)과 정확히 반대 방향으로 좁아진다** —
  다음 사람이 *«가로는 프로토타입으로 확정해도 되겠네»* 로 읽는다.
- **대신 무엇을**: 프로토타입으로 재야 하면 ①**쓰는 유틸리티가 컴파일된 CSS 에 실재하는지 먼저 확인**하고
  (클래스 이름을 보지 말고 **`getComputedStyle` 로 값을 찍어** 확인) ②없으면
  **인라인 스타일로 «가로·세로 양쪽» 을 우회**한다.
- ⚠ **한 축에서 우회 사유를 찾았으면 «나머지 축도 같은 사유에 걸리는가» 를 그 자리에서 점검한다.**
  원인은 «클래스가 없다» 하나인데 **증상은 축마다 따로 나타난다.**
- ⚠ `rem` 기반 간격 유틸리티의 px 값은 **루트 폰트 크기에 달려 있다.** 기본 16px 을 가정한 개산은
  이 프로젝트에서 틀린다(텍스트 확대 검증은 `html{font-size:32px}` 에서 돈다).
  **개산 전에 `getComputedStyle(document.documentElement).fontSize` 를 찍고 그 값으로 환산**하며,
  **그 값을 §5.5 측정 환경표에 «루트 폰트 크기» 항목으로 함께 남긴다**(지금 환경표에 없는 항목이다).

**덤 — 여백 «비율» 을 주석에 적을 때는 클래스가 아니라 계산된 px 로 적는다.**
행 간격은 «표제↔내용 사이» 만이 아니라 **«모든 행 사이»** 에 붙는다. 그래서 클래스 이름으로 적은 비율
(«4:1»)이 화면 참값(«15:3 = 5:1»)과 **달랐다.** 주석의 숫자가 **검산에 쓰이는 순간 사료가 된다** —
**클래스 이름은 비율의 근거가 아니다.**

## 5.10 «재는 쪽» 과 «입력 쪽» — 측정은 옳은데 대상이 달랐다 (2026-09-01 신설)

§5.5~§5.9 는 전부 **«재는 쪽»** 을 다룬다(환경·정의·시점·범위). 이 절은 **«입력 쪽»** 이다 —
**세는 방법은 맞았는데 내가 만든 상태·입력이 내가 믿은 것과 달랐다.**

### 5.10.1 «전부 실패» 규율은 «부분 실패» 를 안 잡는다

§5.6 이 세운 *「전부 실패가 나오면 대상이 아니라 방법을 먼저 의심하라」* 에는 구멍이 있다.

- **성공률이 0 도 100 도 아니면, 「대상의 차이」를 설명하기 «전» 에
  「내가 만든 입력이 매번 같았는가」를 먼저 확인한다.**
- ★ **부분 실패가 전부 실패보다 위험하다** — **성공한 절반이 알리바이가 되어**
  *「지점에 따라 다르다」* 같은 **그럴듯한 설명이 먼저 떠오른다.** 전부 실패였으면 방법을 의심했을 것이다.

> **장면(2026-09-01)**: 거리뷰 지점 6곳 중 4곳이 «침묵» 해 *「거리뷰 모드에서 눌렀는데 아무 일이 없다」* 를
> 결함으로 올리기 직전까지 갔다. 원인은 **둘 다 내 입력**이었다 — ①시트를 닫으면 모드가 꺼지는데
> 2~5번째 클릭은 **모드가 꺼진 상태**였고 ②나머지는 **클릭이 고정 헤더에 맞았다**(5.10.2).
> 헤더를 피해 다시 재니 **8/8 전부 열렸다. 침묵 0.**

### 5.10.2 좌표를 클릭하기 «직전» 에 그 좌표를 무엇이 덮고 있는지 읽는다

- **`elementFromPoint` 를 스크롤·리사이즈 «전» 에 읽고 클릭에 쓰지 마라.**
  그 값은 **클릭 시점의 참값이 아니다**(§5.9.2 와 같은 «언제 쟀나» 계열).
- ⚠ **이 저장소는 모든 페이지에 높이 68px 고정 헤더가 있다.** 지도·캔버스 상단을 노린 클릭이
  **헤더의 로고 링크에 맞아 페이지가 `/` 로 이동**할 수 있다.
- **대신 무엇을**: ①클릭 직전에 `elementFromPoint` 를 **다시** 읽어 대상이 맞는지 확인하고
  ②맞지 않으면 **좌표를 옮긴다**(상자 하단부). ③**페이지가 이동했는지**(`location.pathname`)를
  실패 판정에 함께 넣는다 — 이동은 «오탭» 의 결정적 증거다.

### 5.10.3 «세는 방법이 질문에 안 맞는» 계보 — 축 목록

이 저장소가 반복해 걸리는 형태다. **숫자를 세지 말고 목록으로 유지한다**(숫자는 적는 순간 낡는다).
한 라운드에 **여섯이 다 나왔고, 서로 다른 축이라 아무도 남의 함정에 걸리지 않았다 — 각자 «자기» 축에서 걸렸다.**

| 축 | 무엇을 틀리나 | 예 |
|---|---|---|
| **기준계** | 무엇을 «기준으로» 재는지 안 정했다 | 스크롤하는 문서 안에서 상자 «안» 요소의 이동을 **뷰포트 절대좌표**로 쟀다 → 페이지 스크롤이 「지도 이동」으로 잡혔다 |
