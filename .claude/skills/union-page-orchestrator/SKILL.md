# Union Page Orchestrator

전국금융산업노동조합 코스콤지부 공식페이지의 에이전트 팀을 조율하는 통합 워크플로우. **제1원칙: 검증되지 않은 정보는 조합원에게 게시되지 않는다** — 콘텐츠는 구현 전(1차)과 게시 직전(2차) 두 번의 검증 게이트를 통과해야 한다.

## 실행 모드: 감독자(Supervisor) — 오케스트레이터가 리더

메인 세션이 팀리더다. `Agent` 도구로 팀원을 스폰하고(`run_in_background: true`로 병렬 가능), 후속 조율은 스폰된 에이전트에게 `SendMessage`로 이어간다(컨텍스트 유지). 진행 상황은 `TaskCreate`/`TaskUpdate`로 추적한다.

> `TeamCreate` 도구가 있는 환경이라면 동일 구성을 에이전트 팀 모드로 운영해도 된다. 없는 환경(현재 기본)에서는 위 감독자 방식이 표준이다.

## 에이전트 구성

| 팀원 | subagent_type | 역할 | 스킬 | 출력 |
|------|--------------|------|------|------|
| fact-verifier | `fact-verifier` | 콘텐츠 정밀검증 (1차·2차 게이트) | union-fact-check | `_workspace/01_verifier_factcheck.md`, `05_verifier_final.md` |
| frontend-designer | `frontend-designer` | 디자인 토큰·스펙 설계 | union-design-system | `_workspace/02_designer_spec.md` |
| web-developer | `web-developer` | Next.js 구현 | union-webapp-dev | 소스 코드 + `_workspace/03_developer_impl.md` |
| qa-tester | `qa-tester` | 통합 정합성·접근성 검증 | union-qa-testing | `_workspace/04_qa_report.md` |
| backend-developer | `backend-developer` | NCP 백엔드 설계·구현 | union-backend-dev | `_workspace/06_backend_api_spec.md`, `07_backend_impl.md` |

모든 Agent 호출에 `model: "opus"`를 명시한다 (세션 모델이 더 상위 티어면 생략하여 상속해도 된다).

## 워크플로우

### Phase 0: 컨텍스트 확인 (후속 작업 지원)

1. `_workspace/` 존재 여부 확인
2. 실행 모드 결정:
   - **미존재** → 초기 실행, Phase 1로
   - **존재 + 부분 수정 요청** (예: "디자인만 바꿔줘", "그 공지 문구 수정") → **부분 재실행**: 해당 에이전트만 재호출. 이전 산출물 경로를 프롬프트에 포함해 기존 결과를 읽고 피드백을 반영하게 한다. 콘텐츠 문구가 바뀌면 fact-verifier 재검증도 포함
   - **존재 + 새 입력** → **새 실행**: 기존 `_workspace/`를 `_workspace_prev_{YYYYMMDD_HHMMSS}/`로 이동 후 Phase 1로

### Phase 1: 요청 분류 및 준비

1. 요청 유형을 분류하고 필요한 에이전트만 활성화한다 (전문가 풀 라우팅):

| 요청 유형 | 활성 에이전트 | 경로 |
|----------|-------------|------|
| 콘텐츠 게시 (공지/소식) | verifier → developer → qa → verifier(2차) | 검증 게이트 필수 |
| 신규 기능/페이지 | (콘텐츠 있으면 verifier) → designer → developer → qa | 전체 파이프라인 |
| 디자인 변경 | designer → developer → qa | 검증 게이트 생략 가능 |
| 버그 수정 | developer → qa | 콘텐츠 무관 시 |
| 백엔드/API 작업 | backend-developer → (프론트 연동 시 web-developer) → qa | 아키텍처 미확정 사항은 사용자 확인 후 진행. QA는 API 명세 ↔ 프론트 타입 교차 검증 필수 |

2. `_workspace/` 생성, 사용자 입력(콘텐츠 원문, 요구사항)을 `_workspace/00_input/`에 저장
3. `TaskCreate`로 이번 실행의 작업 목록을 등록한다 (의존 관계 포함)

### Phase 2: 정밀검증 게이트 (1차) — 콘텐츠 포함 시 필수

1. `fact-verifier` 스폰: 입력 콘텐츠 검증 → `_workspace/01_verifier_factcheck.md`
2. 판정 분기:
   - **승인** → Phase 3 진행
   - **조건부 승인** → 수정 요구 사항을 콘텐츠에 반영(리더가 직접 또는 사용자 확인 후) → 진행
   - **반려** → **워크플로우 중단.** 반려 사유와 게시 가능 조건을 사용자에게 보고한다. 반려된 콘텐츠로 다음 Phase를 진행하지 않는다

### Phase 3: 디자인 설계 — 기능/디자인 작업 시

1. `frontend-designer` 스폰: 요구사항 + 승인 콘텐츠 기반 스펙 작성 → `_workspace/02_designer_spec.md`
2. 리더는 스펙에 대비 검증 결과표가 포함됐는지 확인한다. 누락 시 SendMessage로 보완 요청

### Phase 4: 구현 + Incremental QA 루프

1. `web-developer` 스폰: 스펙·승인 콘텐츠 기반 구현. 모듈 완성 시마다 리더에게 보고하도록 지시
2. 모듈 보고를 받으면 `qa-tester` 스폰(또는 기존 인스턴스에 SendMessage): 해당 모듈 + 인접 경계면 검증 → `_workspace/04_qa_report.md`
3. 실패 항목 발생 시: 리더가 `web-developer`에게 SendMessage로 리포트 전달 → 수정 → `qa-tester`에 회귀 검증 요청
4. **수정↔재검증 루프는 모듈당 최대 2회.** 3회째 실패하면 루프를 멈추고 리더가 원인을 직접 분석해 사용자에게 보고한다 (스펙 모순, 요구사항 문제 가능성)

### Phase 5: 최종 게이트

1. `qa-tester`: 전체 통합 검증 (라우팅 전수, 빌드, 접근성)
2. `fact-verifier`(2차): 구현물에 실제 렌더링되는 콘텐츠를 승인 원문과 최종 대조 → `_workspace/05_verifier_final.md`
3. 두 게이트 모두 통과해야 완료다. 하나라도 실패하면 Phase 4의 수정 루프로 돌아간다 (최대 1회, 이후 사용자 보고)

### Phase 6: 보고 및 정리

1. `_workspace/`는 보존한다 (검증 이력·감사 추적용 — 노조 페이지 특성상 "언제 무엇을 근거로 게시했나"가 중요하다)
2. 사용자에게 결과 요약: 게시/구현된 것, 검증 판정 이력, 미해결 항목, QA 미검증 항목
3. 피드백 기회 제공: "결과나 팀 워크플로우에서 개선할 부분이 있나요?" — 피드백은 하네스 진화(에이전트/스킬 수정 + CLAUDE.md 변경 이력)에 반영한다

## 판정 기록 — 리더가 지키는 규율

에이전트가 늘고 왕복이 길어지면 **판정이 메시지 이력에 흩어진다.** 그러면 리더 자신이 상반된 지시를 보내게 된다. 실제로 그렇게 됐다 — 같은 항목(`FIT_PADDING`·상태 패널)을 승인 → 계산 후 뒤집기 → 다시 채택으로 **세 번 뒤집었고**, 그 사이 디자이너 스펙과 메시지가 엇갈려 개발자가 모순된 지시를 받았다.

**규칙:**

- **판정은 산출물에 기록되고, 메시지는 그것을 가리킨다.** "내가 승인했다"가 아니라 "§30.17이 확정본이다"로 말한다. 메시지로만 존재하는 판정은 다음 왕복에서 사라진다
- **뒤집을 때는 무엇을 무효화하는지 명시한다.** 새 판정만 보내면 받는 쪽은 이전 것과 합쳐서 이해한다. **"§30.16.5는 인용 금지"처럼 죽은 절을 이름으로 지목**한다
- **산출물은 지우지 않고 대체 표식을 단다.** 감사 추적이 목적이므로 원문을 남기되, 그 절만 읽는 사람이 낡은 값을 인용하지 않게 한다
- **뒤집힌 판정이 3건을 넘으면 이력표를 만든다.** 어느 절이 유효하고 어느 절이 죽었는지 한 곳에서 읽히게 한다

**낡은 근거가 남아 인용되는 것이 이 프로젝트의 반복 실패 방식이다.** 제거된 지물의 픽셀값이 임계 결정의 근거로 남았고, `확인 중` 문구가 상태 종료 후에도 남아 사용자 지적을 받았다. 판정도 같은 방식으로 썩는다.

### 판정 근거가 조건부 사실이면 조건을 함께 적는다

*"A 가 B 를 대신한다"* 로 무엇을 생략하는 판정을 낼 때, **A 가 항상 성립하는지 확인하고 아니면 조건을 명시한다.** 조건을 안 적으면 다음 사람이 **무조건 참인 사실로 읽고**, A 가 깨져도 그것을 판정과 연결하지 않는다.

실제로 그랬다 — 전체 화면 지도에서 범례를 생략하며 근거를 *"팝업이 같은 문자열을 전달한다"* 로 적었다. 그것은 **팝업이 열릴 때만 참**인데 조건을 안 적었고, 나중에 다른 라벨이 탭을 가로채 팝업이 안 열리자 **조작 결함으로만 처리될 뻔했다.** 그 화면에서는 콘텐츠 은폐였다.

- **같은 사건의 등급이 화면·맥락마다 다를 수 있다.** 한쪽에서 불편인 것이 다른 쪽에서는 위반이다
- **깨짐 경로를 열거한다.** 성격이 다르면(데이터 / 렌더 / 조작) **점검하는 사람도 시점도 다르므로** 나란히 적어야 둘 다 보인다
- 검사 항목으로 승격할 때는 **범위를 좁게 쓰지 마라** — *"라벨이 라벨을"* 로 쓰면 오버레이·새 컨트롤이 빠져나간다

### 회수 규율 — 지표가 흔들리면 파생값까지

측정 지표나 근거가 무효로 판명되면 **그 지표에서 파생된 모든 수치를 함께 회수한다.** 지표 하나만 내리고 파생값을 남기면, 남은 숫자가 독립 근거처럼 인용된다.

이번 실행에서 네 번 나왔다 — 검증자가 정합 잔차 지표를 철회하며 그 지표로 만든 거리값까지 내렸고, 도로 방위 근거를 철회할 때 그것으로 뒷받침한 결론도 함께 내렸다. QA는 제거된 지물의 픽셀값과 재현 실패한 측정값을 격리했다. **회수 대상은 지표가 아니라 그 지표에서 나온 것 전부다.**

### 후속 목록은 해소될 때 그 자리에서 갱신한다

`FOLLOWUPS.md` 같은 이월 목록은 **적을 때가 아니라 해소될 때 썩는다.** 다른 작업이 지나가며 원인을 고쳐도 항목은 그대로 남고, 다음 사람이 그것을 근거로 삼는다.

실제로 그랬다 — QR 카드의 가로 스크롤 원인 두 가지가 이전 라운드에서 이미 처리됐는데 후속 항목이 갱신되지 않아, **리더가 그 낡은 자료를 그대로 설계 판정에 넘겼다.** 디자이너가 소스를 보고 *"지목한 원인이 이미 처리돼 있다 — 고치면 회귀만 만든다"* 로 되돌렸다.

- **부분 해소도 기록한다.** 원인 셋 중 둘이 해소되면 남은 하나를 명시하고 **"원인 미특정"** 으로 상태를 바꾼다
- **원문은 지우지 말고 "인용하지 마라" 표식을 단다** — 발견 당시 기록은 경위 추적에 쓰인다
- **처방보다 특정이 먼저다.** 증상만 남고 원인이 낡은 항목은 **다시 지목하고 나서** 고친다. 이미 처리된 곳을 다시 "고치면" 회귀만 만든다

### 같은 숫자가 다른 계약을 가리킬 때

임계값이 여러 층에 같은 숫자로 존재하면 판정이 섞인다. 이번에 `8px`이 셋이었다 — 재노출 임계(판정에 안 씀) · 접기 스펙 예산(미달 시 경고) · 라벨 배치 여백 하한(미달 시 설계 반송). **숫자가 아니라 계약으로 부르고, 미달 시 무슨 일이 일어나는지를 표로 고정한다.** 하나로 뭉치면 설계에 돌아가야 할 것이 리포트에만 남는다.

### 금지 규칙을 유지하더라도 근거가 바뀌면 근거를 다시 쓴다

이 프로젝트가 반복한 *"근거가 소멸했는데 판정이 안 고쳐졌다"* 의 **거울상**이다. 판정이 유지되면 아무도 조문에 손대지 않는데, **글자가 같아도 그것을 떠받치던 근거는 통째로 바뀌어 있을 수 있다.**

실제로 그랬다 — 배치도 우측 상자의 괄호 숫자를 문안에 *"한 글자도 쓰지 마라"* 로 금지했고, 근거는 **«출처 미확인이라 쓸 수 없다»** 였다. 나중에 사용자가 *"괄호는 테이블 개수라 큰 의미 없는 내용"* 이라고 답해 **뜻이 확정됐다.** 금지 자체는 유지가 맞았지만(§5.3 *"이 문장이 없으면 조합원이 다르게 행동하는가"* 에 걸리지 않는다) 근거는 **«미확인이라 못 쓴다» → «확인됐으나 쓸 필요가 없다»** 로 갈렸다.

- **바뀐 근거를 조문 옆에 적는다** — 산출물의 조건표와 **소스 주석 양쪽**에. «유지»만 적으면 근거가 낡은 채로 남는다
- 적을 것은 **«확인 여부»가 아니라 «필요 여부»가 금지의 근거**라는 구분이다. 안 적으면 다음 사람이 *"이제 확인됐으니 써도 되겠다"* 로 뒤집는다
- **판정을 «유지 / 유지(근거 교체) / 강등 / 폐기» 로 구분해 적는다.** «유지» 한 낱말이 앞의 둘을 함께 덮으면, 근거가 바뀐 쪽이 아무 표시 없이 지나간다

### 근거가 여럿이던 판정에서 하나가 죽으면 남은 근거의 강도를 다시 적는다

**결론이 유지된다고 근거표를 그대로 두지 마라.** 회수 규율(파생값)이 판정에서 «아래로» 흐르는 것이라면 이것은 «옆으로» 흐른다 — 뒷받침 하나가 죽으면 결론은 살아도 **그 결론의 강도가 달라진다.**

실제로 그랬다 — 무대 대응 관계 판정의 뒷받침이 **2개에서 1개로 줄었다.** 제2 근거였던 *"지부 배치도의 화살표가 같은 구역을 찍는다"* 가, **그 배치도를 지부가 직접 그렸다는 사실이 확정되면서 «독립 자료»가 아니게 됐다**(우리와 같은 추론을 한 제3자일 뿐이다). 결론은 유지됐다 — 남은 근거(자료가 무대 위치를 스스로 «산업은행 옆» 이라 명명 + 지붕까지 92 m vs 145 m 실측)가 단독으로 결정적이었다. 검증자는 등급을 **«독립 2급 근거» → «제3자의 동일 판단» 으로 정직하게 강등**했고, 이후 판본이 교체되자 그 근거를 **이름으로 «인용 금지»** 처리했다.

- **강등도 판정이다.** 근거 등급표를 다시 적고 «결론 유지 · 근거 (ii) 강등» 처럼 **무엇이 유지되고 무엇이 내려갔는지**를 나눠 쓴다
- **죽은 근거는 표에서 지우지 말고 이름으로 인용 금지 처리한다.** 지우면 «왜 결론이 지금 이 강도인가»를 추적할 수 없다

**★ 뒤집힘이 쌓이면 이력표로는 부족하다 — 구현자에게는 «자족적 확정본»을 준다.** 위 «뒤집힌 판정이 3건을 넘으면 이력표» 규칙의 다음 단계다. 이번 실행에서 조건표가 **§40 → §41 → §42 → §43 → §44 → §47 → §48 로 7회 갱신**됐고 **죽은 절이 14건**이었다. 그 상태로 «이력을 따라오라»며 넘기면 **구현자는 낡은 절을 인용한다.**

- **구현 착수 전에 «이 절 하나만 읽고 구현한다» 절을 새로 쓴다.** 앞 절을 가리키지 말고 **조건 전체를 다시 적고, 축자 문면은 코드블록으로 싣는다**
- 남기는 상호참조는 **«근거» 열의 절 번호뿐** — 읽지 않아도 구현이 되는 감사 추적용이다
- **«인용 금지» 목록을 그 절 안에 함께 박는다.** 다른 파일이나 앞 절에 두면 확정본만 읽는 사람에게 닿지 않는다

### «못 고치는 것» 을 «고쳤다» 고 적지 마라 — 그리고 «못 고친다» 만 적어도 안 된다

이 프로젝트는 QA 쪽에 **«못 재는 것을 통과로 적지 않는다»**(`union-qa-testing §5.8.3`)를 이미 갖고 있다. ★ 이것은 그 **거울상**이다 — **«못 고치는 것을 고쳤다고 적지 않는다».** 리더가 건 게시 조건이 **수단 부재로 달성 불가**로 판명되면, 그 조건을 «충족» 으로 닫는 순간 산출물이 거짓이 된다. 그리고 산출물의 판정은 다음 세션이 인용하는 사료다.

> **장면(2026-08-29)**: 리더가 게시 조건을 걸었다 — *"대상 명칭이 시각과 «같은 줄»에서 갈리게 하라."*
> 디자이너가 실측했다: 그 문자열을 한 줄에 담으려면 슬롯 **303.8px** 이 필요한데 200% 모바일 슬롯은 **201px** 이고,
> 303.8px 슬롯은 **뷰포트 463px 부터** 나온다 — **선언 뷰포트 360·390·412 가 전부 갈린다.**
> 문면은 사용자 지정이라 못 바꾸고 여백도 못 줄인다. **조판 수단 자체가 없었다.**
> 디자이너가 *"막을 수 없는 것을 «막았다»고 적지 않았습니다"* 로 되돌렸다.

★★ **그런데 «못 고친다» 만 적어도 안 된다.** 한쪽만 적으면 **오독이 각각 따로** 난다:

| 하나만 적으면 | 다음 사람의 오독 | 그래서 하는 일 |
|---|---|---|
| **«수단이 없다» 만** | *"그럼 실패네"* | **되돌리려 든다** — 목적을 이미 달성한 구현을 뒤엎는다 |
| **«목적을 달성했다» 만** | *"그럼 원래 조건대로도 되겠네"* | **문면·여백을 만진다** — 못 건드리는 것을 건드린다 |

**규칙:** 조건이 수단 부재로 달성 불가면 **① «수단이 없다» 와 ② «목적은 무엇으로 달성됐다» 를 «한 벌» 로** 적고, **죽은 조건 문면을 이름으로 지목**한다(뒤집기 규율과 같다).

- **«수단이 없다» 는 «막힌 수단을 열거해» 세운다.** 시도할 수 있는 수단을 전부 적고 각각 왜 막혔는지를 한 줄씩 단다(사용자 지정 문면 · 스펙 하한 · 접근성 판정선 · 원문 보존 등 **막은 규칙의 이름**). **하나라도 «안 해 봤다» 가 남으면 «수단 부재» 가 아니라 «미시도»** 다 — 이 절을 쓰지 마라
- ①은 **«어렵다» 가 아니라 실측으로** 적는다 — **필요량 · 가용량 · 그 가용량이 나오는 경계** 셋. 경계를 적어야 다음 사람이 *"이 범위에서는 불가능하다"* 를 **판정**할 수 있고, 범위가 바뀌면(뷰포트·배율·문면 길이) 되살릴 수 있다
- ②는 **조건이 아니라 목적**에 대고 적는다. 조건은 목적의 한 수단일 뿐이라, **수단이 죽어도 목적은 다른 수단으로 살아 있을 수 있다**
- ★ **목적이 조건보다 «더 강하게» 달성될 수 있다.** 그때도 조건을 «충족» 으로 적지 마라 — **«조건 미달성 · 목적은 다른 경로로 달성»** 이 참이다. (이번 건의 ②는 *"200% 에서 첫 줄이 «전 조합원» 이라 대상이 시각보다 먼저 읽힌다 — 애초 우려한 오독 방향과 반대"* 였다.)
- ⚠ **②를 못 적으면 «폐기» 가 아니다.** 조건도 목적도 미달성이면 판정은 **«미해결»** 이고 **후속 목록에 올린다**(«후속 목록은 해소될 때 그 자리에서 갱신한다» 절). «폐기» 는 **②가 실제로 적힌 경우에만** 쓴다 — 안 그러면 이 절이 실패를 닫는 통로가 된다
- 판정 이름은 **«유지 / 유지(근거 교체) / 강등 / 폐기»** 중 **폐기**다. **조건은 폐기하고 목적은 남긴다** — 나중에 수단이 생겼을 때 되살릴 것은 조건이 아니라 목적이다

### 원문과 화면이 달라지는 지점은 «순서·열·묶음» 세 축으로 센다

원문 자료를 화면으로 옮기면 «원문 구조 변경» 이 생기고, 리더는 그것을 열거해 최종 게이트에 올린다. 그런데 **리더는 눈에 띄는 축 하나만 센다.** 축이 셋이라는 것을 모르면 **나머지 둘은 «변경» 으로 인식되지도 않는다** — 빠뜨린 것이 아니라 애초에 안 보인다.

> **장면(2026-08-29)**: 리더가 최종 게이트에 «원문 구조 변경» 을 **2건** 올렸다(행 순서 · 블록 순서).
> **검증자가 3건이라고 정정했다** — 빠진 것은 **표가 3열(시간/내용/비고) → 2열이 되어 「비고」 열이 통째로 사라진 것**이었다
> (인명이 내용 칸 «안» 으로 들어갔다). 승인은 났지만(**사실 손실 0** · 근거는 접근성 실측)
> **리더의 목록에는 없었다.** **«순서» 만 세고 «열» 을 안 셌다.**

**규칙:** 원문을 화면으로 옮길 때 달라지는 지점을 **세 축으로 나눠 열거**한다. 축마다 따로 세지 않으면 **안 센 축은 «없는 것» 이 된다.**

| 축 | 무엇이 달라지나 | 예(2026-08-29) |
|---|---|---|
| **순서** | 항목이 나오는 차례 | 행 순서 역전 · 블록 순서 교체 |
| **열** | 표·목록의 «칸» 구성 | 3열 → 2열(한 열이 통째로 소멸) |
| **묶음** | 무엇이 무엇과 한 덩어리인가 | 소멸한 열의 내용이 다른 칸 «안» 으로 들어감 |

**최종 게이트에 올릴 목록을 만들 때 세 축을 «각각» 세고, «0 건» 인 축도 «0» 이라고 적는다.** 축이 목록에서 통째로 빠지면 다음 사람은 **«0 건» 과 «안 셌음» 을 구분할 수 없다** — 이번 누락이 정확히 그것이다.

⚠ **문자열이 그대로여도 이 셋은 «원문 구조 변경» 이다.** 축자 게이트는 이것을 못 잡는다 — **`grep` 은 순서·열·묶음을 세지 않는다.** 소스 문자열 집합 차분이 **0 이어도 세 축은 전부 바뀌어 있을 수 있다.**

⚠ **«대신 무엇을»**: 열거한 **각 건을 최종 게이트에 «항목으로» 올려 검증자가 판정하게 한다.** 리더가 *"사실 손실이 없으니 괜찮다"* 로 혼자 닫지 마라 — 혼자 닫으면 산출물에 남는 것은 «괜찮다는 판정» 이 아니라 **«목록에서 사라짐»** 이다. 이번에 리더는 그렇게 닫아서 **한 건을 통째로 빠뜨렸고, 검증자가 세지 않았으면 게이트에 오르지 않았다.**
