## 3. 완화 조치 이행 확인 — 채널명 구분 표기

검증자가 조건부 승인 2건에 건 **필수 조건**: "카드에 채널명을 노출해 금융노조 제작물이
아님을 구분할 것." 프로덕션 렌더 마크업 실측:

```
오바마 대통령이 말하는 노조 ↗
  2026.08.17 · 하종강의 노동과 꿈
  외부 링크(새 창) · www.youtube.com

노조가 필요한 이유 ↗
  2026.08.17 · 마이크임팩트
  외부 링크(새 창) · www.youtube.com
```

금융노조 공식 3건은 `금융노조 교육문화본부`/`금융노조` 로 찍혀 **외부 채널 2건과 즉시 구별**된다.
이 표시가 곧 게이트 조건의 이행이다.

**이 조건은 구현 단계에서 한 번 무력화될 뻔했다** — `PostList.tsx:98` 이 `source` 를
`!isExternal` 일 때만 렌더하고 있었고, 노동교육 5건은 전부 링크형이라 채널명이 어디에도
표시되지 않는 상태였다. 리더 실측으로 발견 → §15.6R-D 로 2행 메타 재설계 → 반영.
**검증 게이트를 통과한 조건이 구현 단계에서 조용히 사라질 수 있다**는 사례로 기록한다.

### 5-1. 6·7 검증 — 파노라마 좌표가 실제로 5번 출구다

**부수 확인 — 초기 시야 방향이 맞다.** `pan: 130°` 는 "의사당대로 남동쪽(대오 방향)"이라는 주석의 값이다.
5번 출구에서 대오 1 밴드 남동단까지 실제 방위각을 계산하니 **131.5°** 였다(대권 방위각).
**1.5° 차이 — 초기 화면이 조합원이 걸어갈 방향을 정확히 향한다.**

### 5-2. §0.4 검사 — 모달이 지도를 숨기지 않는가

7회차·8회차가 반복해 확인한 은폐 위험이라 **실제로 열고 닫아 봤다.**

|---|---|
| SSR HTML 의 `<dialog>` 에 `open` 속성 | **없음** — 닫힌 상태로 시작. 스크린리더에 `닫기`·sr-only 문구가 새지 않는다 |
| 모달 열림 | `dialog.open === true`, `aria-label` 정확, **포커스가 `닫기` 로 이동** |
| 모달 안 표시 문자 | `로드뷰는 시각 자료입니다…` + `닫기` — **로드뷰에만 있는 정보 0** |

### 5-3. 기록 — 로드뷰는 과거 촬영본이다 (게시 저해 아님)

페이지는 로드뷰 촬영 시점을 밝히지 않는다. 그러나 ① 문구가 **무엇이 보인다고 주장하지 않고**

## 3. 판정이 필요했던 항목 — 3건 전부 승인

### 3-1. 새 창 고지 문면 차이 — **승인**

내 승인본은 `(새 창으로 열립니다)` 였고 구현은 `외부 링크(새 창) · map.naver.com` 이다.

- **의미가 같고 정보가 늘었다** — 새 창 고지는 그대로이고 **목적지 도메인이 추가**됐다
- 조합원이 누르기 전에 **어디로 가는지** 아는 것은 §10-7 이 요구한 바로 그 취지다
- 온누리 카드와 **같은 규칙**(표시 도메인을 `href` 에서 파생 — `NAVER_DIRECTIONS_DISPLAY_HOST`)이라
  링크와 표시가 갈릴 수 없다. 사이트 안에서 외부 링크가 한 가지 방식으로 보인다
- **URL 전문을 노출하지 않은 것도 옳다** — 내부 인코딩 문자열이라 판독 가치가 0이고 소음이다

### 3-2. 각주 2줄이 링크 카드 **아래**로 밀렸다 — **렌더 확인 후 승인**

9회차 §9-5 는 각주 2줄을 **`<dl>` 바로 아래**로 지정했다. 구현은 그 사이에 링크 카드가 들어갔다:

```
장소  국회의사당역 5번 출구 메인무대 앞
[ 네이버 지도로 길찾기 카드 (3줄) ]
※ 20:30 은 코스콤지부의 참가 계획입니다. …
※ 2차 출석은 20:00~21:00 입니다. …
```

각주 1 은 `<dl>` 의 `코스콤지부 20:30까지 참가 계획` 행을 해설하는 문장이라, **떨어지면
"조합원은 두 블록을 이어 읽지 않는다"(6·7회차 반복 판정)에 걸릴 수 있다.** 그래서 실제로 렌더해 봤다.

**390px 모바일 스크린샷 결과 — 끊기지 않는다.**

| 검사 | 결과 |
|---|---|
| 같은 패널 안인가 | **그렇다.** 링크 카드는 흰 패널 **안**의 연한 테두리 라운드 카드다. 패널을 가르는 분리선이 아니다 |
| 한 화면에 함께 보이는가 | **그렇다.** 390px 에서 `20:30까지 참가 계획` 부터 각주 2 까지 **스크롤 없이 전부 보인다** |
| 각주가 자립하는가 | **그렇다.** 각주 1 이 `※ **20:30 은 코스콤지부의** 참가 계획입니다` 로 **수치와 주어를 스스로 다시 밝힌다** — 9회차에서 의도한 중복이 여기서 값을 한다 |
| `18:30` 위계 | **유지.** `text-hero` 는 페이지에 **1개소**뿐이고 그 내용이 `18:30` 이다 |

개발자가 남긴 배치 근거(링크는 `장소` 에 묶이고 `※` 는 시각에 묶이며, 마지막 자리는 당일 행동인
2차 출석이 갖는다)도 타당하다. **승인하되 제약을 남긴다 → 요구 80.**

### 3-3. 링크 제목의 `text-primary`(파랑) — 요구 13 위반 아님

블록 1 에 처음으로 유채색 텍스트가 들어왔다. 요구 13 은 **"색 강조는 출석 시각 2개에만"** 이다.

- 요구 13 이 규율하는 것은 **원문 형광펜에 대응하는 강조색**이고, 링크색은 **링크임을 알리는 관례적 어포던스**다. 성격이 다르다
- 크기는 `text-body`(본문급)이고 **대형 수치를 만들지 않았다.** `18:30` 은 `text-ink`(검정)이라 **위계 역전이 없다**
- `accent`(오렌지 — 온누리·CI 전용) 미사용 확인

## 4. ★ 요구 68 의 2단계 이월 — **정당하다. 요구 73 과 모순되지 않는다.**

리더가 판정을 요청한 핵심이다. 요구 73 은 *"라벨 폭 부족을 `예정` 삭제로 풀지 마라"* 였다.

### 요구 73 이 금지한 것과 실제로 일어난 것은 다르다

| | |
|---|---|
| **요구 73 이 금지한 것** | `5번 출구 (메인무대 예정)` → `5번 출구 **(메인무대)**` — 새 정보를 붙였다가 **`예정` 만 떨어뜨리는 축약** |
| **실제로 일어난 것** | ① 라벨이 **원래 문자열 `5번 출구` 그대로**다. 붙였다 줄인 것이 아니라 **아직 붙이지 않았다** |

**렌더 전수 검사**: `(메인무대 예정)` **0건**, **`(메인무대)` 도 0건**.
→ 요구 73 이 막으려던 최악(= `예정` 없는 `(메인무대)` 가 확정 등급 실선 도트에 올라가는 것)은 **발생하지 않았다.**

### `예정` 이 화면에서 사라진 곳이 **0곳**이다

| 자리 | `예정` |
|---|---|
| 지도 라벨 ② | `메인무대**(예정)**` |
| 범례 ① | `메인무대는 이 앞에 설 **예정**입니다` |
| 범례 ② | `주최측 설치 **예정**` |
| 무대 카드 | `설치될 **예정**입니다` |

**문자열을 줄인 것이 아니라 표면을 옮긴 것**이라는 리더의 정리가 맞다.

### 오히려 이 상태가 요구 8 을 **더 잘** 지킨다

요구 8(4회차)은 *"확인 좌표와 예정 위치를 시각적으로 구분 + 범례"* 다.

내가 요구 69 를 **필수**로 건 이유는 *"① 라벨에 무대 정보가 붙으면 실선 도트(확인 등급)에
미확정 정보가 섞이니 범례가 구분을 져야 한다"* 였다. **그 전제가 1단계에서는 성립하지 않는다** —
① 라벨에 무대 정보가 붙지 않았으므로 **지도 위에서 확정도가 섞이는 일 자체가 없다.**

→ 요구 69 는 이제 **"위험을 상쇄하는 안전장치"가 아니라 "사용자 의도를 범례에서 전달하는 단독 수단"** 이다.
부담이 줄었고, 확정 등급 기호는 **오염 0** 이다.

### 범례 ①②가 둘 다 메인무대를 말한다 — **충돌 검사 통과**

8회차에서 각주와 ⑥ 범례의 충돌을 잡았던 것과 같은 유형이라 확인했다.

| 행 | 말하는 층위 |
|---|---|
| ① `메인무대는 이 앞에 설 예정입니다` | **무대와 출구의 관계** — 어느 근처인가 |
| ② `주최측 설치 예정. 정확한 지점이 확정되지 않아…` | **무대 지점의 정밀도** — 얼마나 정확히 아는가 |

- **모순 없음.** 둘 다 `예정` 을 명시하고, 서로 다른 것을 말한다
- ① 의 `이 앞에` 가 ② 의 `정확한 지점이 확정되지 않아` 보다 확정적으로 들릴 여지가 있으나,
  **원문 §1 이 장소를 `국회의사당역 5번 출구 메인무대 앞` 으로 확정 서술**했고
  **무대 카드가 이미 `메인무대는 국회의사당역 5번 출구 앞에 설치될 예정입니다` 를 게시 중**이다(4회차 승인·배포됨).
  **새 주장 0 — 승인된 문장의 반복이다**
- 8회차가 문제 삼았던 "떨어져 있어 서로를 부정하는 것처럼 읽힘"도 없다. **①② 는 범례에서 인접한 두 행**이라 나란히 읽힌다

### 다만 — 요구 68 은 **미이행 상태로 남는다**

사용자 요청(`5번출구는 (메인무대)임을 표시`)이 1단계에서는 **범례로만** 충족되고 **지도 라벨 위에는 없다.**
이것은 **사실 오류가 아니라 요청 충족도** 문제이므로 **게시를 막지 않는다.** 판단은 리더·사용자 몫이다.
2단계 팝업이 이월분을 받으므로 **조건을 지금 못 박는다 → 요구 79.**

## 4. ★ 조건 — 15회차 요구 122·123 미이행. **두 건이 서로를 모순시킨다**

교통 안내 범위 밖이지만 **같은 화면에 함께 게시된다.** 최종 게이트는 나갈 화면 전체를 본다.

### 발견

```
page.tsx:164   <dt>집회 시간</dt>  <dd>18:30 ~ 20:30</dd>
page.tsx:208   ※ 20:30 은 코스콤지부의 참가 계획입니다. 주최측 식순상 폐회선언은 20:20~ 입니다.
```

| 요구 | 지시 | 현재 |
|---|---|---|
| **123** | **`참석 시간`**. **`집회 시간`·`행사 시간` 금지** | **`집회 시간`** — 금지어가 쓰였다 |
| **122** | **각주 1 전체 삭제**(요구 100 흡수) | **살아 있다** |

### 왜 게시를 막는가

**① `집회 시간 … 20:30` 은 사용자가 명시적으로 부정한 사실을 주장한다.**
사용자 원문: ***"현재 계획상 20:20이 공식 행사종료"***.
`집회 시간` 이 20:30까지라고 쓰면 **집회가 20:30에 끝난다는 주장**이고, **사용자 본인 진술과 모순**된다.
15회차 §15-2 가 이 표기를 금지한 이유가 정확히 이것이다.

**② 각주 1 은 사용자가 "쓸데없는 사족"으로 지목해 삭제를 지시한 문장이다.**
`_workspace/00_input/content-rally-20260828.md` §6.8.1 의 삭제 지시 대상 2건 중 하나다.

**③ ★ 그리고 지금 이 둘이 서로를 부정한다.**

| 화면 | 20:30 의 성격 |
|---|---|
| `<dt> **집회 시간**` | **집회가** 20:30까지 |
| 각주 1 | **코스콤지부의** 참가 계획 |

**같은 수치에 두 개의 다른 성격이 한 화면에 있다.** 8회차에서 각주와 ⑥ 범례 충돌을 잡은 것과 같은 유형이고,
**이번은 같은 숫자를 두고 갈리므로 더 명백하다.** 조합원이 어느 쪽으로 읽어야 할지 알 수 없다.

> **참고**: `page.tsx:199` 개발자 주석은 각주 1 이 **이미 삭제된 것으로 서술**한다
> (*"…삭제를 지시했고, `집회 시간 | 18:30 ~ 20:30` 으로 교체됐다"*). **주석과 코드가 어긋났다.**
> 교체는 됐는데 **각주 제거가 누락**된 것으로 보인다.

### 조치 — 요구 122·123 이행으로 **둘 다 해소된다**

```
<dt>집회 시간</dt>  →  <dt>참석 시간</dt>            (요구 123)
page.tsx:208 각주 1  →  삭제                        (요구 122)
```

- `18:30 ~ 20:30` **값과 sr-only 장형은 무수정** — 사용자 요청 표기 그대로다
- `참석 시간` 은 **주최측 종료를 주장하지 않으면서** 사용자 요청 표기를 담는다.
  `참석` 은 페이지 제목(`…결의대회 **참석** 안내`)의 용어라 **창작 0**(15회차 §15-2)
- 각주 1 이 사라지면 **모순도 함께 사라진다**

그리고 **요구 137(문자열 한 벌)을 더 잘 지킨다** — 같은 URL이 두 이름으로 존재하던 것이 하나로 정리됐다.

### 7-3. ★ 요구 112 리스크가 배포를 막는가 — **막지 않는다**

리더 견해에 동의한다. 근거를 정리한다.

**① 지금 문안은 참이다.**
`5번 출구` 는 원문 §1 과 §6.9 배치도가 **교차 확인한 집결 기준점**이고,
`급행은 국회의사당역에 서지 않습니다` 는 **노선 사실(1급)** 이다.
**최근접역이 바뀌어도 이 문장 자체는 거짓이 되지 않는다** —
거짓이 되는 것은 `WAYFINDING.station` 을 **여의도역으로 치환했을 때뿐**이고,
개발자 주석과 `expressSkipsStation` 플래그가 정확히 그것을 막고 있다(요구 143).

**② 리더 서술을 한 군데 정정한다.**
*"여의도역이 최근접역일 수 있다"* 는 **아직 미검증 가설**이다 —
12회차 §12-4·13회차 §13-6 에서 내가 **조건부로 남긴 것**이고 좌표로 확인한 바 없다.
**확정된 사실이 아니라 가설을 근거로 배포를 미루는 것은 순서가 뒤집힌 것이다.**

**③ 없는 것보다 낫다.**
현재 페이지에 교통 안내가 **아예 없다.** 8/28 까지 7일이고 조합원은 지금 이동 계획을 세운다.
그리고 국회의사당역 ↔ 여의도역은 **9호선 한 정거장 차이**다 —
완전히 다른 방향으로 보내는 것이 아니라 **한 정거장 더/덜 가는 문제**다.

**④ 갈아끼우기가 이미 구조로 대비돼 있다.**
역·출구·URL·플래그가 `WAYFINDING` **한 객체**에 있어 바뀌면 한 곳만 고친다.

### 7-4. ⚠ 다만 미리 경고한다 — 역이 바뀌면 **URL도 재도출해야 한다**

최근접역이 여의도역으로 바뀌면 길찾기 링크의 **도착지도 바뀌어야 한다.**
그런데 그 URL의 좌표부(`3zf71R,2AKrxU`)는 **네이버 내부 인코딩**이다.

> **역 이름 문자열만 바꾸면 도착 핀은 5번 출구에 그대로 꽂힌다.**
> 화면의 도착지 이름과 실제 핀이 어긋나는데 **에러가 나지 않는다** — 요구 78과 같은 유형의 **조용한 고장**이다.

**재도출 방법은 10회차 §10-6 에 있다**(레거시 엔드포인트 리다이렉트 왕복 → 모바일 UA로 좌표 복원 확인).
**소수 좌표 형식으로 바꾸지 마라** — 마포구 성산동을 보여준다(요구 74).
