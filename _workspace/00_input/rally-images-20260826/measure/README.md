# 리더 실측 — 신구 지도 이미지 대조 (2026-08-26)

측정 스크립트는 세션 스크래치패드에서 실행했다(`sharp` 로 원시 픽셀 접근).
크롭 2장(`crop-before.png` · `crop-after.png`)은 **같은 지리 영역**을 같은 배율로 잘라 나란히 볼 수 있게 한 것이다.
크롭 파라미터: `map.png` 기준 `left=620, top=540, w=560, h=600` / `rally-layout.png` 는 배율 `1077/1374` 환산.

## M-1 · 두 이미지의 **베이스는 같은 배치도**다 [측정]

- 최적 정렬 탐색(배율 0.80~1.25 · 오프셋 ±80px, 좌상단 55% 영역 기준):
  **최적 배율 1.00 · 오프셋 (dx 0, dy −2)** — 즉 **같은 크롭 영역**이다. 배율만 1077 → 1374(1.276배).
- 색상 도형 bbox 대조(공통 538폭 환산):

  | 도형 | BEFORE | AFTER |
  |------|--------|-------|
  | 노랑 테두리 | x14~501 · y30~468 | x14~498 · y31~465 |
  | 초록 면(3구역·무대3) | x75~498 · y0~466 | x75~495 · y0~463 |
  | 파랑 면(2구역·무대2) | x0~486 · y14~469 | x0~537 · y13~466 |
  | 빨강 면(1구역·무대1) | x17~433 · y45~403 | x17~430 · y44~400 |

  → **구역 폴리곤이 같은 자리에 있다.** 이전 게시물과 구역 경계가 달라지지 않았다.

- 다만 **픽셀 동일 파일은 아니다**: 정렬 후에도 그레이스케일 MAD ≈ 17.3 이 남는다.
  위성 타일 렌더가 다른 **재캡처본**이다(크롭 2장을 나란히 보면 배경 채도·건물 그림자가 다르다).
  ⚠ **이 사실을 "구역이 바뀌었다"로 읽지 마라** — 위 bbox 표가 반대를 말한다.

## M-2 · 추가된 코스콤 표시의 **정확한 위치** [측정 + 육안]

`crop-after.png` 참조. 주황 사각형은 **2개**이고, 둘 다 **3구역의 북서쪽(무대3(LED) 쪽) 끝**에 있다.

- **왼쪽 사각형**: 3구역 폴리곤 **안**. 3구역의 **맨 앞(무대3 쪽) 끝**에 붙어 있다.
- **오른쪽 사각형**: 3구역의 **동쪽 경계선을 넘어** 바깥(3구역 ↔ KDB산업은행 사이 띠)까지 걸친다.

★ **이것이 이번 반영이 새로 말하는 정보다.** 종전 이미지·본문은 *"3구역"* 이라는 **띠 전체**(길이 약 250~400 m)를
말했는데, 신규 이미지는 **그 띠 안의 앞쪽 끝**을 찍는다. 조합원이 3구역 뒤쪽 끝에 서는 것과
앞쪽 끝에 서는 것은 **현장에서 100 m 이상 차이**다.

⚠ **오른쪽 사각형이 경계를 넘는 것을 우리가 해석하지 마라.**
`official.jpeg` 우측 상자에 `코스콤(1)` / `산업은행 인도` 가 따로 있어 *"2개 사각형 = 대오 + 인도 배치"* 로
읽고 싶어지지만 **근거가 없다.** 손그림 표시의 부정확일 수도 있다. **추정을 문안으로 만들지 마라.**

## M-3 · 파생값 영향 [리더 1차 판단 — 검증자가 확정할 것]

`page.tsx` 의 `약 230 m` 와 `_workspace` 파생 근거(`5번 출구 ↔ 3구역 최근접 249 m ~ 최원 396 m`)는
**좌표 기반**이라 이미지 교체로 직접 흔들리지 않는다. 다만 M-2 가 **"3구역 어디쯤"을 좁히므로**
`약 230 m` 가 가리키는 지점과 이미지가 찍은 지점이 **같은 곳인지** 검증자가 대조해야 한다.

## M-4 · 인코딩 옵션별 용량 실측 [측정 2026-08-26]

`sharp` 로 원본에서 직접 인코딩. **Next `<Image>` 가 (현행 `unoptimized` 아님) 요청 시 WebP 로 재인코딩하므로
`webp90` 열이 조합원이 실제로 받는 무게에 가깝다.** `jpeg92`/`png` 열은 **저장소에 커밋되는 원본**의 무게다.

### 리더 소견 (개발자가 §0.6 로 확정할 것)
- **조합원이 받는 무게는 둘 다 문제없다** — 360px 단말 기준 map 193KB + official 39KB.
- **저장소 원본**은 `map.png` 3.2MB 가 유일한 무게다. 위성사진이라 손실 압축에 적합하고
  (`page.tsx` 주석이 `unoptimized` 를 쓰지 않는 근거로 이미 그렇게 적고 있다),
  **1374 폭 JPEG q92 = 497KB** 로 6.5배 줄어든다. 다만 이미지 안에 흰 로고 박스의 검은 글자가 있어
  **JPEG 링잉**이 생길 수 있다 — 바꾼다면 로고 부분을 확대 대조하고 결정하라.
- ⚠ **현행 폭 상한 `sizes="(min-width: 768px) 832px, 100vw"` 를 그대로 쓸 경우**,
  데스크톱 2x 는 1664px 를 요구하는데 `map.png` 원본이 1374px 다 — **업스케일되지 않고 1374 가 최대**다.
  기존 이미지(1077px)보다는 나아졌다. 이 사실을 알고 `quality`/`sizes` 를 정하라.
- ⚠ `official.jpeg` 는 **재인코딩하지 마라.** 이미 JPEG 이고 239KB 다. PNG 로 바꾸면 437KB 로 늘고,
  JPEG→JPEG 재인코딩은 문자 가장자리만 나빠진다.

## M-5 · 모바일 실제 표시 크기 판독성 [실측 2026-08-26]

**표시 폭 계산**: 360px 뷰포트 → `max-w-page px-4`(32px) = 328 → 카드 `p-5`(40px) = **288 CSS px**.
그 폭으로 실제 축소한 것이 `m288-map.png` · `m288-official.png` · `m288-before.png` 다. **눈으로 확인했다.**

| 이미지 | 288px 표시 높이 | 판독 결과 |
|--------|----------------|-----------|
| `m288-before.png` (현행) | 266px | 구역 라벨(`집회 3구역`)이 **띠를 따라 회전돼 있어 얼룩으로 보인다** — 종전 리더 실측과 일치 |
| `m288-map.png` (신규) | 265px | 구역 라벨은 **여전히 판독 불가**. 그러나 **`koscom` 로고·주황 화살표·주황 사각형은 또렷하게 읽힌다** |
| `m288-official.png` (신규) | 388px | **지부명이 전혀 판독되지 않는다.** 무대 3칸(노랑)과 표의 전체 골격만 구분된다 |

### M-5.1 ★ 신규 지도는 **모바일 판독성 결함을 실제로 고친다**

`page.tsx` 블록 2 주석에 이 페이지의 **핵심 실측 근거**가 이렇게 적혀 있다:

> `break.png` 를 360px 단말 표시 크기(328×303)로 축소하면 **`집회 3구역` 라벨이 띠를 따라 회전돼 있어
> 얼룩으로 보인다. 글자로 인식되지 않는다.**

그 판정은 **신규 이미지에서도 라벨에 대해서는 그대로 참**이다. **그러나 `koscom` 표시는 다르다** —
로고 박스는 수평 흰 바탕에 큰 글자이고, 화살표·사각형은 고채도 주황 면이라 **288px 에서 살아남는다.**
→ **신규 지도는 «위치를 읽는 도구»로서 종전 이미지보다 실질적으로 낫다.**
⚠ 다만 이것을 *"이제 문장이 필요 없다"* 로 확대 해석하지 마라 — 사각형이 **3구역 어디쯤인지**는
   288px 에서 구역 라벨을 못 읽으므로 **그림만으로는 «3구역»이라는 이름과 연결되지 않는다.**

### M-5.2 ⚠ `official.jpeg` 는 모바일에서 **읽을 수 없다** — 설계 판정 필요

288px 에서 `코스콤(한국증권전산)지부` 를 **찾을 수 없다.** 종전 배치도가 판독 불가여도 괜찮았던 근거는
*"이 이미지의 역할은 «위치 안내»가 아니라 «출처 증거»"* 였는데(§36.9-1),
**지부별 배치도는 조합원이 «우리 지부 어디»를 찾으려고 들여다볼 자료**라 같은 논리가 그대로 성립하지 않는다.

디자이너가 판정할 것: ① 그대로 둔다(역할=참고 자료, 위치는 위 지도·본문이 진다) /
② 확대 경로를 준다(새 탭 원본 열기 등) / ③ 다른 처리.
⚠ ②를 택하더라도 **모달·라이트박스를 새로 만드는 것은 범위 초과**다. 이 페이지에는 이미 지도 전체화면이 있다.

## M-6 · `official.png` (1209×1665 PNG · 92KB) 인코딩 실측

| 폭 | jpeg q92 | webp q90 | png |
|----|---------|---------|-----|
| 750 (모바일 360px·2x) | 98KB | **54KB** | 207KB |

★ **네이티브 폭 PNG(61KB)가 WebP(100KB)보다 작다.** 표 그림은 **평면 색·날카로운 문자**라 PNG 가 유리하다.
축소본에서 PNG 가 커지는 것은 안티에일리어싱이 그러데이션을 만들기 때문이다.
→ 원본을 **PNG 그대로 두는 것이 옳다.** JPEG 로 바꾸지 마라(문자 가장자리만 나빠진다).

## M-7 · `official.png` 모바일 판독성 — **여전히 판독 불가** [실측]

`m288-official-new.png` — 288 CSS px 표시 시 **397px 높이**. **지부명이 전혀 판독되지 않는다.**
구판(jpeg)보다 렌더가 깨끗하지만 **판독 가능선을 넘지 못한다.**
→ **검증 조건 6(확대 경로)은 신판에서도 그대로 필요하다.** 디자이너 판정 대상.

## M-8 · ⚠ 현행 `sizes` 를 그대로 쓰면 확대 경로가 막힌다

블록 2 현행: `sizes="(min-width: 768px) 832px, 100vw"`.
`official.png` 에 이것을 그대로 쓰면 **데스크톱이 받는 변형이 832px 로 묶인다**(원본 1209px).
표 글자를 읽으려면 **원본 해상도에 닿는 경로**가 있어야 한다 — 검증 조건 7 이 지목한 함정이 이것이다.

# ⛔ M-9 · **회수 — `288px` / `832px` 은 틀린 값이다** (2026-08-26 · 디자이너 실측으로 발견)

## 무엇이 틀렸나

위 §M-5 · §M-7 · §M-8 과 `_workspace/02_designer_spec.md` §36.11-3 이 쓴
**`288 CSS px`(360 뷰포트) · `832 CSS px`(데스크톱)** 은 **루트 폰트 16px 를 가정한 값**이다.

**이 사이트의 기본 루트는 12px 다.**

> `src/app/globals.css:115-121`
> ```css
> html {
>   /* ★ 기본 75%(사용자 지시 2026-08-22 — "폰트크기는 슬라이더 좌측끝을 기본값으로").
>      rem 토큰이 전부라 글자·여백·제목·모서리가 함께 75% 로 내려간다 */
>   font-size: 75%;
> }
> ```

`px-4`(1rem)·`p-5`(1.25rem)가 **rem 이라 함께 0.75배**가 된다 —
16px·20px 가 아니라 **12px·15px** 다. 그래서 슬롯 폭 계산이 통째로 틀렸다.

| 1280 뷰포트 이미지 슬롯 | **624 px** | ~~832 px~~ |

| 파생 진술 | 종전 | **정정** | 결론 |
|-----------|------|---------|------|

| 캡션/간격 픽셀(§36.11-1) | ~~12px / 24px~~ | **9px / 18px** | **유지** — **비율 1 : 2 는 그대로**라 판정 불변 |

★ **`m288-*.png` 렌더 파일들은 실제보다 좁게(288 vs 306) 그린 것**이라 **판독 불가 결론은 보수적**이다.
   파일을 지우지 않는다(경위 추적). **다만 «288px 이 표시 폭이다» 로 인용하지 마라.**

## ★ 이 정정이 만든 새 규율 — 폭 상한 금지는 «취향»이 아니라 **측정된 경계**다

데스크톱 판독이 **8.8px** 이면 **하한선 근처**다. `md:max-w-[560px]` 같은 폭 상한을 두면
**7.9px 로 떨어져 판독이 죽는다.** → §36.11-5 의 «폭 상한을 두지 마라»는
**560px 이라는 실측 경계**를 갖는다. 취향으로 뒤집지 마라.

## ⚠ QA 에게

**12px / 24px / 288px / 832px 로 재면 «틀린 실패»가 난다.**
측정 환경표에 **루트 `font-size` 실측값**을 반드시 적어라(`getComputedStyle(document.documentElement).fontSize`).
이 항목이 없어서 리더가 전 라운드 계산을 틀렸다.
