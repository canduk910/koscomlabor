# 11. `~` 코드포인트 — **못 쟀다. 그러나 위험이 «한 방향»이라 안전한 쪽으로 고정한다** (리더 2026-09-01)

⚠ **§8-2 를 «해소»로 바꾸지 마라.** v3 원본이 저장소에 없어 **여전히 못 쟀다.** 아래는 «판정»이지 «측정»이 아니다.

## 실측한 것
```
v2 식순 소스 구분자:  '-' U+002D × 17   ·   '~' U+007E × 8      ← 둘 다 ASCII
v3 전사본 구분자:      '~' U+007E × 6                            ← 전사자(리더)가 ASCII 로 적었다
TimeText 정규식:      /[-~]/  → ASCII 만 잡는다
```
★ **v2 식순의 ASCII `~` 는 «원본 이미지 대조를 통과한» 값이다**(검증 §69-1 · 개발자 원본 재판독).
**같은 작성자·같은 문서군**이라 v3 도 ASCII 일 개연이 높다. ⚠ **개연이지 확정이 아니다**(§5.8.2 — 구판에 기댄 판정).

## ★ 판정 근거 — **틀렸을 때의 손실이 대칭이 아니다**

| 원본이 | 우리가 ASCII 로 쓰면 | 우리가 전각으로 쓰면 |
|---|---|---|
| **ASCII** | ⭕ 정확 | ⛔ **원문 변경 + `TimeText` 불발 → 200% 겹침** |
| **전각 `～`** | ⚠ 원문 표기 미세 차이(시각적으로 거의 동일 · **조합원 영향 0**) · `TimeText` **정상** | ⭕ 정확하지만 **`TimeText` 불발 → 200% 겹침** |

→ ★★ **어느 경우에도 ASCII 가 «덜 나쁘다».** 전각은 **맞아도 결함**을 만든다.
**ASCII `~` 로 고정한다.** ⛔ **정규식을 `～`(U+FF5E)까지 확장하지 마라** — 그것은 «전각을 써도 된다»를 여는 것이고, 원본 확인 «전에» 열면 안 된다.

## 원본이 들어오면
1. 구분자 코드포인트를 판독한다. 2. **전각이면** — 문면을 바꾸기 «전에» `TimeText` 확장이 200%에서 실제로 듣는지 **먼저 실측**하라. **문면과 정규식을 동시에 바꾸지 마라**(무엇이 회귀를 냈는지 못 가른다).

# 12. ★★ 규율 후보 2건 — `alt` (검증 §73 · `doc-commit` 에서 `union-webapp-dev` 로)

## 12-1. **화면 기준 방향은 `alt` 에서 «지상 방위 주장»이 된다**

| 계층 | 「오른쪽 차도」가 무슨 뜻인가 |
|---|---|
| 시각 사용자 | **화면의 오른쪽** — 사진을 보고 있으니 화면 참조가 성립한다 |
| ★ **비시각 사용자** | **지상의 오른쪽/동쪽** — **사진을 못 보므로 «화면의 오른쪽»이라는 개념 자체가 없다.** 낭독되는 순간 **지상 방위로만** 읽힌다 |

> **규칙**: `alt` 에 **`오른쪽`·`왼쪽`·`위`·`아래`** 같은 **화면 기준 방향**을 쓰지 마라.
> **대신 무엇을**: **방위가 확정된 것은 방위로**(`남쪽` — 실측 근거가 있을 때) · 없으면 **관계로**(`…와 … 사이`) ·
> 그것도 없으면 **말하지 않는다.**

★ **이 저장소에서 특히 위험한 이유**: `오른쪽 차로`·`동측`·`서측` 은 **이미 기대 0 인 금지어**다
(*「카메라가 어느 차로에 있었는지 모른다」* · 게시 조건 49·53). **화면 참조로 쓴 한 낱말이 «금지된 사실 주장»이 된다.**
⚠ **리더가 초안에서 실제로 걸렸다**(「오른쪽 차도」·「왼쪽 건물」 둘 다).

## 12-2. **`alt` 는 그림 속 «글자의 전사»가 아니라 그림이 전달하는 «정보»의 등가다**

★★ **정정 경로가 계층마다 다르다** — 이것이 핵심이다.

> 배치도 원본은 북단 무대를 **`메인무대`** 라 부르고 우리 페이지는 **`무대 1`** 이라 부른다.
> - `메인무대` 를 쓰면 → **기대 0 위반** + ★★ **비시각 사용자만 «현장 표지판과 다른 이름»을 얻는다.**
>   시각 사용자는 범례·pill·본문이 전부 `무대 1` 이라 **정정되지만 `alt` 만 듣는 사용자는 정정 경로가 없다.**
> - `무대 1` 을 쓰면 → **이미지에 «없는 글자»** 다.

★★★ **셋째 길: 그 대상을 «이름으로 부르지 않는다».**
이미지의 **행동 정보**는 «코스콤이 어느 구역인가»이고 **북단 무대의 이름은 그 정보에 없다.**
→ 이미지에 있는 `무대 2` 는 쓰고 · 이미지에 있는 `메인무대` 는 안 쓰고 · 이미지에 없는 `무대 1` 도 안 쓴다.

> **규칙**: 그림 속 낱말과 우리 낱말이 갈릴 때는 **①어느 쪽을 쓸지 고르기 «전에» ②그 대상을 «부를 필요가 있는지»** 를 먼저 묻는다.
> ⚠ **두 이미지의 처분이 갈리는 것이 정상이다** — 같은 라운드의 지도 이미지는 원본 라벨이 `무대 1` 이라 **거기선 쓴다.**

브라우저가 이미지 후보를 고르는 시점은 **CSS 적용 «전»(프리로드 스캐너)** 이고 그때 `rem` 은 **초기값 16px** 이다.
→ **`sizes` 의 `4.5rem` = 54px 이 «아니라» 72px** 이다.

**QA 실측(6조건 · 16px 모델과 6/6 일치)** — 두 표기가 **두 조건에서 갈린다**:
| 조건 | 슬롯 | `54px` 판 | `4.5rem` 판 | |
|---|---|---|---|---|
| 320 / dpr3 | 266 | **828** ⭕ | **750** | ❌ 48px 부족(6.0%) |
| 390 / dpr2 | 336 | **750** ⭕ | **640** | ❌ 32px 부족(4.8%) |

⚠ **손실은 «전송량»이 아니라 «판독»이다** — 이 두 장은 **판독 대상이 걸린 이미지**이고
(`화장실 : …(시청역, 스벅 등) 이용` · `PAUL BASSETT` 간판) **판독 생존 확인은 `w=1080` 기준으로 했다.**

### ★ 내 «루트가 바뀐다» 우려는 «참»이었지만 **`rem` 도 그것을 못 푼다**
`FontScaleControl` 이 런타임에 루트를 바꾸는 것은 사실이고 **실제 슬롯도 줄어든다**(실측 306 → 279).
**그러나 `sizes` 는 그 변화를 «어느 표기로도» 추종할 수 없다** — 평가 시점이 CSS 이전이다.
→ **정직한 결론: `sizes` 는 런타임 루트 변화를 못 따라간다. 그러니 «기본 배율에서 정확한» px 을 쓴다.**
⚠ **«덜 나쁜 쪽»을 고르는 문제였지 «따라가는 표기»가 있는 문제가 아니었다.**

### ★★ 새 규율 — **«같은 값의 두 표기»가 «평가 시점»에서 갈린다**
`4.5rem` 과 `54px` 은 이 페이지에서 **CSS 상 같은 값**인데 **`sizes` 라는 다른 평가 시점에서 갈렸다.**
이 저장소의 **«같은 이름 다른 양»** 계보에 **«같은 값 다른 평가 시점»** 을 더한다.
> **규칙**: 값이 **CSS 밖에서 평가되는 자리**(`sizes` · `media` 속성 · 프리로드 힌트)에는
> **문서 CSS 에 기댄 단위를 쓰지 마라.** ⛔ 특히 `rem` — **초기 16px 로 평가된다.**
> **대신 무엇을**: **절대 단위로 쓰고, 그 값의 «유래»와 «어느 배율 기준인가»를 주석에 적는다.**

⚠ **리더가 이 자리에서 틀렸다.** 근거로 낸 «실측»이 **레이아웃 폭**을 잰 것이라
**`sizes` 가 평가하는 값이 아니었다** — 이 저장소가 세어 온 **«대상» 축 오류**다.

# 15. ★★★ 규율 후보 — **«수신자가 존재하지 않는 지시»** (개발자 명명 · 2026-09-01)

## 장면
개발자가 `sizes` 에 `calc(100vw - 54px)` 를 넣고 주석에 이렇게 적었다:
> *「지금은 확정값 `54px` · **루트 폰트가 바뀌면 다시 재라**」*

★ **문장 자체는 참이다.** 루트가 바뀌면 실제로 다시 재야 한다.
★★ **그런데 «다시 잴 사람»이 없다** — 루트 폰트를 바꾸는 것은 **코드 변경이 아니라 «조합원의 런타임 조작»** 이다
(`FontScaleControl.tsx:72` 가 `document.documentElement.style.fontSize` 를 직접 바꾸고 `localStorage` 에 저장한다).
**조합원이 슬라이더를 움직이는 순간 그 지시를 수행할 개발자는 그 자리에 없다.**

## 이 저장소가 세어 온 실패 유형 «어디에도 없는» 축이다
| 기존 축 | 무엇이 문제인가 |
|---|---|
| 낡은 근거 | **참이었다가 죽었다** |
| «원래부터 틀린» 근거(M-74) | **한 번도 참이 아니었다** |
| 축이 없는 값(§13) | **참인데 어느 기준인지 없다** |
| ★ **수신자 없는 지시** | ★ **참이고 기준도 있는데 «수행할 사람이 그 시점에 없다»** |

> **규칙**: *「…하면 다시 재라 / 확인하라 / 갱신하라」* 를 적을 때는
> **«그 사건이 일어나는 시점에 그것을 할 사람이 있는가»** 를 묻는다.
> - **빌드·배포·자료 교체** → ⭕ 사람이 있다. 지시가 성립한다
> - **런타임 사용자 조작 · 외부 서버 상태 변화 · 시각 경과** → ⛔ **사람이 없다**
>
> **대신 무엇을**: ① **코드가 스스로 따라가게 만든다**(이번 건: `px` → `rem`) ·
> ② 못 하면 **감시 장치**를 만든다(빌드 가드 · 테스트) · ③ 그것도 못 하면
> **«수신자 없음»을 명시**하고 **후속 목록으로 올린다.** ⛔ **주석에 적고 끝내지 마라 — 아무도 안 읽는 시점에 발동한다.**

⛔ **[정정 2026-09-01] 종전에 «이번 건은 ①로 풀렸다(`rem` 이 따라간다)»고 적었다. 틀렸다** — §14 참조.
**`sizes` 는 «어느 표기로도» 런타임 루트 변화를 못 따라간다**(평가 시점이 CSS 이전 · `rem` 은 16px).
→ ★ **이번 건은 ①이 «불가능»한 사례다.** 실제 처분은 **③ «수신자 없음을 명시하고 후속으로»** 였다:
**기본 배율에서 정확한 `54px` 을 쓰고, «어느 배율 기준인가»와 «왜 `rem` 이 아닌가»를 주석에 남긴다.**
⚠⚠ **규칙 자체는 살아 있다** — 오히려 **더 강해진다**: 「코드가 스스로 따라가게 만든다」가
**«늘 가능한 것이 아니다»**. 가능한 줄 알고 «따라가는 표기»를 골랐다가 **더 나쁜 값**을 얻었다.

# 16. ★★ 규율 후보 — **새 규율은 «다음 사람»보다 «지금 나»에게 먼저 적용된다**
